## 🟠 PT-28-02 — lookup `CharacterObject_*` ломает не только вассалов

**Уверенность: ТОЧНО для создания вассала и респека ребёнка; ВЕРОЯТНО для

Сегодня:

```text

203d91ac... — Гутраг / CharacterObject_11342
c1a95768... — Кульят / CharacterObject_9762
```

маркер отказа стёрт поздним ACK, но мод-лог 27.07 доказывает её
`heir_not_found`.

кланов**:

```text

```

Сегодняшние новые фантомы: id 6 и 7. По backend-логам API-счётчик
`kuro_gothic` в течение стрима вырос с 1 до 2 и 3, хотя обе попытки мод
отклонил.

Крустики не потеряны: действие имеет `price=0`. Динары также не списаны —
обработчик падает на lookup в `VassalHandlers.cs:76-89`, а проверка и списание
250 000💰 начинаются позже, после `VassalHandlers.cs:92`.

### Респек ребёнка

Сегодня один зритель дважды выбрал ребёнка, которого backend считает
принадлежащим ему:

```text
CharacterObject_11314 → hero_not_found → возврат 500💎
CharacterObject_11346 → hero_not_found → возврат 500💎
```

За всё время `hero.respec_child_skills`: **3 попытки из 3 провалились**,
каждый раз деньги вернулись.

Общий корень виден в коде:

- `VassalHandlers.cs:76` — `MBObjectManager.Instance.GetObject<Hero>(heirId)`;
- `FamilyHandlers.cs:41` — тот же вызов в общем `FindHeroByStringId`;
- `FamilyHandlers.cs:298` — через него проходит респек ребёнка.

Тот же helper используют rename ребёнка, изменение внешности и активация брака.
Их поломка логически вероятна, но сегодня они не вызывались, поэтому помечены
не как подтверждённые, а как радиус проверки.

Вывод: задача в `DEFERRED` должна называться не только «lookup наследника для
вассала», а «единый resolver динамических Hero для всех family/vassal/heir
операций».
