# План завершения frontend freeze для Claude Code

Основание: FRONTEND_FREEZE_READINESS_AUDIT_2026-09-11.md, прочитан 11.09.
Проверенный при составлении HEAD: c23bcb8. Это задание на следующие работы,
а не утверждение, что они уже сделаны, и не разрешение на Submit for Review.

## Уточнения к аудиту

- /dev/extension.html не является предусмотренным маршрутом. В dev_login.py
  определены /dev и /dev/preview; последний перенаправляет авторизованного
  пользователя на /frontend/extension.html. Не добавлять маршрут ради устранения
  этого 404. Исправлять только действительно найденные неверные ссылки в документах.
- Неизвестный deployed revision и непроверенный Hosted Test — пробелы в доказательствах,
  а не подтверждённые дефекты. Сначала проверить, затем решать, нужен ли выкат.
- 0050f18 уже исправляет три найденные гонки. Не писать исправление повторно.
- Размер всех распакованных файлов ZIP не равен сетевой загрузке mobile entrypoint.
  Фактический initial load измеряется отдельно с учётом запросов API и ресурсов.
- Метки P1 в отчёте объединяют ошибки кода и релизные условия. В журнале работ
  различать «дефект исправлен» и «проверка ещё не выполнена».

## 1. Зафиксировать исходные условия

Проверить git status/HEAD и текущие release-документы. Не трогать чужие изменения.
Проверить ZIP и immutable-copy штатным verify-candidate. Ожидаемый SHA-256:
6f7e115bfd8bdabbd254a4c1f42cf730961d56f06da0523161d3a54ab43da253.
Ожидаемый MD5: 059806841c3b84790af97c1056c4c3f5.
При отличии установить причину и назвать новую проверяемую версию, не переносить
автоматически результаты аудита на другой ZIP.

Приёмка: в журнале есть commit, оба хеша, размер и результат проверки кандидата.

## 2. Контракт зафиксированного клиента 0.0.5

Добавить воспроизводимую проверку совместимости, привязанную к SHA-256 immutable
ZIP, а не к текущему frontend tree. Сохранить существующую проверку 0.0.1.
Не ограничиваться поиском строк в исходниках или существованием endpoint.

Из точного архива проверить потребителей ответов для:
- auth resolve и viewer state;
- config: цены, лимиты, availability;
- catalog и progressive expected_price;
- quests/cases и notices;
- результатов платных запросов, отказа и восстановления после ошибки.

Серверные ответы получать от настоящих обработчиков на временной БД. Там, где
необходим DOM, использовать изолированный браузерный стенд с клиентом из ZIP.
Внешний Twitch/игру допустимо подменять на границе, сами проверяемые обработчики
и клиентскую интерпретацию ответов не заменять фиктивным успешным результатом.

Приёмка: неизменный клиент работает при изменённой серверной цене, допустимом нуле,
отсутствующем необязательном поле, дополнительном поле и отказе API; несовместимый
ответ в отрицательном контроле действительно валит тест. Проверка включена в CI.
Описать, какие контракты покрыты и какие остаются ручными.

## 3. Подтвердить серверное исправление гонок

Прогнать test_module_action_races.py на выбранном release commit. Убедиться, что
проверяются TTL против dispatched/acked, poll против refund и requeue против ACK.
После изменений тестов/инфраструктуры выполнить обязательные проверки проекта.

Read-only проверить production: наличие исправленных функций и вызывающих мест,
соответствие файлов release revision, успешный запуск текущего процесса после
обновления. Не считать один /health доказательством revision.
Если сервер отстаёт, подготовить точный backend-only пакет и порядок отката;
публиковать только при наличии разрешения владельца на этот выкат.
Аварийные/race тесты не запускать на боевых данных.

Приёмка: код, проходящий тесты, соответствует работающему серверу; frontend ZIP
не изменён. Для доказательства использовать хеши файлов и данные запуска,
не добавлять публичный диагностический endpoint без необходимости.

## 4. Закрыть механизм заморозки

После выбора финального ZIP записать связку исходный commit → ZIP SHA-256 → версия.
Тег должен указывать на проверенную точку, существующий тег не передвигать.
Обновить комментарии deploy-lock и проверить dry-run:
- backend-only разрешён;
- default/frontend публикация блокируется при включённой заморозке;
- /dev использует серверный frontend и не является отдельным staging;
- публикация будущего dev UI не подменяет записанный immutable candidate.

Приёмка: защита подтверждена исполняемой проверкой/dry-run, не только комментарием.
Включение режима freeze привязать к реальному состоянию выпуска и записать дату.
Не менять auth/CSP/игровые правила в рамках этой задачи.

## 5. Один приёмочный прогон в Hosted Test

Владелец или агент с разрешённым доступом загружает точный ZIP, сверяет MD5
в Dev Console и записывает доказательство. Не заменять это проверкой /dev.

Обязательное ядро: вход и identity sharing; восстановление авторизации/сети;
viewer state; desktop и Twitch mobile; покупка → реальный эффект → ACK;
отказ → один возврат → уведомление; offline; cases/quests; Config и инструкции
ревьюеру. Пройти существующий checklist без создания параллельного списка истин.
Для каждого пункта записать PASS/FAIL/UNCHECKED, среду и время. Опасные сценарии
дублирования/краша доказывать изолированными тестами; не ломать боевую игру ради них.

Mobile: проверить доступность вкладок и закрытия окон в настоящей оболочке,
измерить initial load. Малые кнопки и подписи оценить до окончательной заморозки:
если нужная функция недостижима, это блокер. Если доступна, остаточный UX-риск
явно записать; не начинать общий редизайн. Любая правка ZIP требует нового хеша
и повторения затронутых проверок.
