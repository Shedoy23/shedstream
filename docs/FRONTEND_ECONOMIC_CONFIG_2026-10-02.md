# Экономические данные и медленная сеть: checkpoint 2, 02.10.2026

Продолжение после `ede7517`. Этот кандидат заменяет первый пакет для принятия
в рабочую ветку: отдельно исправлена найденная при дополнительной проверке
регрессия медленного polling. Первый архив сохранён как исторический snapshot,
не переписан. Всё локально, без push, deploy, установки модов и замены Twitch ZIP.

## Что изменилось

- Четыре дорогих действия получают обязательные цены из существующего config:
  создание клана, создание королевства/восстание, создание вассального клана
  из наследника, найм вассального клана
- При неизвестной, отрицательной или неверно типизированной цене submit
  недоступен. Законный серверный ноль сохраняется. Рядом причина и
  «Обновить цены»; повторная загрузка сохраняет имя и выбранного наследника
- Проверки есть у Click/Enter/общего dispatcher, а у найма повторяются после
  подтверждения. Ответ старой конфигурации не заменяет новый контекст
- Дипломатия больше не заводит выдуманные 300 секунд после ошибки. Она
  использует общую шкалу времени от серверных cooldown fields. Старый buff
  request не стирает принятый позднее cooldown; новый серверный снимок может
  законно его очистить
- Hero/vassals/buffs принимают завершившиеся ответы монотонно: новая ещё
  незавершённая загрузка не делает каждый предыдущий результат бесполезным.
  Старый ответ после уже принятого нового, редактор, принятое действие,
  stop и смена JWT/идентичности по-прежнему ограждены
- Cache stamp обеих будущих оболочек обновлён одинаково (`202610021325`)
- Готовый React preview содержит MIT notices для bundled React/ReactDOM/Scheduler;
  build gate сверяет их с зафиксированными пакетами

Новых API, schema или игровых правил этот этап не вводит. Backend и мод
сохраняют текущую повторную проверку условий и списание. Подробная карта
четырёх actions, config keys и остаточных hardcodes имеет один дом:
[экономический inventory](frontend-economy/README.md).

## Почему понадобился второй polling-фикс

Первый checkpoint отбрасывал результат, если уже начался более новый запрос.
При cadence 8 секунд и latency 9 секунд каждый ответ поэтому пропадал:
старый исходный код рисовал данные, а checkpoint 1 мог оставлять экран пустым.
То же воспроизведено у buffs с 2.5/3 секундами. Теперь сравнивается принятый
результат, а не просто факт начала ещё одного запроса; отдельные barriers
защищают editor и принятые действия. Отрицательный контроль воспроизведён на
предыдущих SHA, исправление независимо проверено на объединённом `1a15c8b`.

## Цена не является атомарной квитанцией

Клиент не подставляет fallback для выбранных четырёх семей и замечает изменение
локально загруженной metadata за время подтверждения. Но текущий action
контракт не принимает expected-price/config_revision для этих действий.
Если сервер изменил цену между GET и POST, он применит своё текущее значение.
Не заявляем гарантию равенства показанной и списанной цены. Backward-compatible
проверка согласованной цены до списания остаётся отдельным будущим этапом.

Остальные scalar/table fallback, другие игры, ограничения/доступность и игровые
каталоги НЕ переведены полностью; см. точный inventory. Настоящие gameplay
факты должны приходить мод→backend→frontend, перенос копии строки в Python
сам по себе этого не доказывает.

Usage-счётчики сохраняют прежнее определение: действия учитываются при входе
в общий dispatcher; запрет до него (например неизвестная цена или невалидное
имя) не является отправленной попыткой. Открытия соответствующих форм
учитываются отдельно. Отсутствие попыток при недоступной функции нельзя
трактовать как отсутствие интереса.
