# Пост-стрим триаж — полная методика

Что делать после стрима, чтобы поймать поломки раньше зрителей. Документ
самодостаточный: его можно целиком отдать другой модели или человеку.

Создан 2026-07-28 по просьбе владельца — после того как триаж 27.07 нашёл
поломку, которая жила три недели, и нашёл её **случайно**. Ниже — и порядок
действий, и ровно те ловушки, из-за которых её не находили раньше.

---

## 0. Главный принцип

**Ищи не сообщения об ошибках, а несостоявшиеся события.**

Поломка этого проекта почти никогда не выглядит как падение. Типичный вид:
прод отвечает 200, тестов красных нет, логи без трассировок — а платная
механика молча не работает. Так умер магазин RimWorld, так три недели терялись
награды за очки канала, так с мая уходила в никуда телеметрия браков.

Поэтому вопрос триажа не «были ли ошибки», а **«что перестало происходить»**.

## 2. Порядок проверок

Идти сверху вниз: сначала деньги и тишина, потом косметика.

### 2.1 Прод не падал

```bash
grep -c 'Traceback' /var/log/twitchbot.err.log
grep -cE '" 5[0-9][0-9] ' /var/log/twitchbot.out.log
supervisorctl status twitchbot
curl -s -o /dev/null -w '%{http_code}\n' https://shedoy23.ru/health
```
Хорошо: 0, 0, RUNNING, 200.

⚠️ **`/health` доказывает только живость базы.** Он был зелёным весь день
27.07, пока все страницы стримера отдавали 500. Проверяй страницы отдельно:
```bash
for p in / /extension.html /overlay.html /privacy.html /terms.html; do
  printf '%s ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' "https://shedoy23.ru$p"; done
```
`privacy.html` и `terms.html` — URL из заявки в Twitch, их падение = отказ на ревью.

⚠️ **Этой проверки НЕ ХВАТАЕТ: дашборд стримера в список не входит, а 27.07
падал именно он** — страницы за авторизацией curl'ом снаружи не достать. Их
проверяет только отрисовка шаблона на самом проде:
```bash
ssh root@31.130.132.224 "cd /root/twitch-extension/backend && ../venv/bin/python -c \"
import jinja2, pathlib
t = jinja2.Template(pathlib.Path('templates/streamer_dashboard.html').read_text(encoding='utf-8'), autoescape=False)
print('шаблон рисуется, символов:', len(t.render()))\""
```
Падение здесь = 500 на дашборде. Именно так ловится «библиотека не доехала».

### 2.2 Деньги: платили и не получили

Главная проверка триажа. **Раздел переписан 2026-07-28** после разбора: первая
версия пропускала PB-02 и принимала ранний ACK за успех.

**Про окно времени.** `date('now')` режет по полуночи UTC, а не по границам
стрима: у ночного эфира половина событий уедет в соседние сутки. Брать окно от
начала стрима:
```sql
SELECT MAX(started_at) FROM stream_sessions;   -- начало последнего стрима
```
и дальше подставлять его вместо `date('now')`.

**а) Застрявшие платные действия — не только `queued`.**
```sql
SELECT type, status, COUNT(*)
FROM module_actions
WHERE status IN ('queued','dispatched')
  AND created_at < datetime('now','-10 minutes')
GROUP BY type, status;
```
Три поправки к очевидному варианту: `dispatched` тоже застревает (мод забрал и
не подтвердил); свежие строки нормальны, поэтому порог 10 минут; **фильтровать
по `json_extract(data,'$.price') > 0` НЕЛЬЗЯ** — см. ловушку ниже.

⚠️ **Отсутствие цены — это не «бесплатно», это красный флаг.** Проверено на
проде 28.07: у сломанной ветки (PB-01) поля `price` в `data` НЕТ вообще.
Фильтр `price > 0` по данным выбросил бы ровно те строки, ради которых пишется
запрос. Поэтому разделять три случая:
```sql
SELECT type,
       CASE WHEN json_extract(data,'$.price') IS NULL THEN 'ЦЕНА ПОТЕРЯНА'
            WHEN CAST(json_extract(data,'$.price') AS INTEGER) > 0 THEN 'платное'
            ELSE 'бесплатное' END AS цена,
       COUNT(*)
FROM module_actions
WHERE status IN ('queued','dispatched')
  AND created_at < datetime('now','-10 minutes')
GROUP BY 1,2;
```

**б) Возврат объявлен, но фактически нулевой.**
```sql
SELECT type, error_msg, COUNT(*) c
FROM module_actions
WHERE error_msg LIKE 'REFUNDED:0%'
GROUP BY type, error_msg ORDER BY c DESC;
```
Считать отдельно от обычных возвратов: в общей статистике `REFUNDED:0`
выглядит как успешный возврат, хотя денег не вернулось.

⚠️ **Но не всякий `REFUNDED:0 (no_price)` — находка.** У честно бесплатных
действий (`hero.add_focus`, `hero.add_attribute`, `hero.reequip_gear`,
`hero.join_tournament` — они платят динарами, крустики не берут) это норма, и
таких строк сотни. Находка — только если у типа есть НЕнулевая цена в
`ACTION_PRICES_DEFAULT` (`routes/bannerlord.py`). Так отделились настоящие
74 случая PB-01 от сотен законных.

**в) Зависшие доменные состояния — их `module_actions` НЕ показывает.**
```sql
SELECT id, policy_id, requested_at, action_id
FROM bannerlord_policy_requests
WHERE status='pending' AND requested_at < datetime('now','-10 minutes');
```
Именно этот класс пропустила первая версия документа: заявка на закон живёт в
своей таблице, и её вечный `pending` не виден ни по очереди, ни по возвратам.
Проверять так же всё, у чего есть собственный жизненный цикл: заявки, аукционы,
предложения, отложенные эффекты.

**г) Сравнить отказ мода с тем, что сохранила БД.**

Поздний ACK способен стереть `error_msg`, поэтому запрос по `REFUNDED:%` может
не увидеть уже состоявшийся возврат. На стриме 28.07 мод отправил 20
`action.failed`, а в БД осталось только 19 строк с ошибкой.

```bash
grep -c 'event action.failed' "$LOG"
```

Сравнить с количеством строк за то же окно:

```sql
SELECT COUNT(*)
FROM module_actions
WHERE created_at >= '<START_UTC>'
  AND error_msg IS NOT NULL;
```

Если числа расходятся, извлечь `action_id` из строк
`[ActionFeedback] REFUND request` и проверить каждый id в `module_actions`.
`status='acked', error_msg IS NULL` при наличии REFUND в backend-логе —
доказанный стёртый маркер, а не успешное действие.

⚠️ **`viewers.db` — текущий баланс, а не история денег.** Отдельного журнала
списаний нет. PB-01 это доказал: поле с ценой потеряно, и точную сумму ущерба
восстановить невозможно в принципе. Не обещай точных цифр по базе — считай
номинал по ценам в коде и честно говори, что это оценка.

### 2.3 Механика, которая перестала встречаться ← ЛОВИТ ТИХУЮ СМЕРТЬ

**Приём, которого не хватало три недели.** Не ищем ошибку — спрашиваем у каждой
механики, когда она работала последний раз.

```sql
SELECT type, MAX(created_at) AS последний_раз, COUNT(*) AS всего
FROM module_actions GROUP BY type ORDER BY последний_раз;
```
Смотреть на ВЕРХ списка: механика, которой не было неделями, либо мертва, либо
не нужна — и то и другое стоит знать.

⚠️ **Оговорка, без которой запрос обманывает.** `created_at` — момент СОЗДАНИЯ
заявки, то есть «кнопку нажали и запрос сохранился». Он **не доказывает, что
в игре что-то произошло**: мёртвый обработчик в моде продолжает исправно
получать новые действия, и по этому запросу механика выглядит живой.
Доказательством служит только терминальное состояние с наблюдаемым эффектом:
```sql
SELECT type,
       MAX(CASE WHEN status='acked' THEN created_at END) AS последний_УСПЕХ,
       MAX(created_at)                                   AS последняя_ПОПЫТКА
FROM module_actions GROUP BY type
ORDER BY последний_УСПЕХ;
```
Расхождение колонок = заявки идут, результата нет.
**И даже `acked` успехом не является** — мод подтверждает ДО реальной работы
(см. RUNBOOK «ACK мод-действия не доказывает выполнение»). Окончательный ответ
даёт только эффект: строка в доменной таблице, отметка в логе мода, изменение
состояния героя.

**Для внешних интеграций смотреть таблицу доставки, а не заявок:**
```sql
SELECT MAX(redeemed_at) FROM channel_points_log;   -- награды за очки канала
```
Здесь запись появляется по факту начисления — именно поэтому запрос вскрыл
27.07, что награды не приходят с 8 июля.

### 2.5 Лог мода: падения и отказы

```bash
LOG="…/ModLogs/bannerlordlink_ГГГГММДД.txt"
grep -E "CRASHED|Exception" "$LOG" | sed 's/.*\] //' | sort | uniq -c | sort -rn | head
grep -E "REFUSE" "$LOG" | sed 's/.*\] //' | cut -c1-70 | sort | uniq -c | sort -rn | head
```
`SWALLOWED …`, `finalizer registered`, `Global crash hooks installed` — это
защита работает, не находка. Настоящее — `CRASHED`, повторяющиеся `REFUSE`
одного вида, `TaskCanceledException` (обрыв связи с бэком: событие потеряно
без повтора).

### 2.6 Проверка того, что чинили последним

Под каждый свежий фикс — своя строка в логе. Пример 27.07 (#38, дипломатия):
```bash
grep -cE "неактуал|no longer relevant" "$LOG"      # ожидание: 0
grep -E "\[diplo-war|\[diplo-ppeace" "$LOG" | tail
```
Фикс без такой проверки остаётся «дедуцированным, не доказанным».

## 3. Ловушки — почему поломки не находились

Каждая стоила реального времени. Проверяющему их знать обязательно.

**Греп по слову «error» пропускает поломки.** Сообщение
`⚠️ OAuth refresh failed: 400 Invalid refresh token` печатается через `print()`,
уровня логирования не имеет, слов `Traceback`/`[ERROR]` не содержит. Проверка
«свежих ошибок» честно показывала **0** при **448** таких строках. Фильтр ищет
словарь, а не важность. → Считай ПОВТОРЫ: одинаковая строка сотни раз — сигнал
сильнее одиночного `ERROR`:
```bash
awk '{$1="";$2=""; print}' /var/log/twitchbot.out.log | sort | uniq -c | sort -rn | head -20
```

**Трассировки лежат в другом файле.** `twitchbot.out.log` их не содержит —
смотреть `twitchbot.err.log`. 27.07 я объявил «падений нет», глядя не туда.

**Время на сервере — UTC.** Лог, обрывающийся «пять часов назад», может быть
абсолютно свежим. Сверяй: `date` на сервере.

**Токен в базе зашифрован** (`enc:…`). Проверка значения из колонки даёт
**401 на исправном токене** — ложная тревога. Брать только через
`get_fresh_oauth_token`, готовый вердикт — в `preflight.ps1`.

**Индикатор может отвечать не на тот вопрос.** Плитка «OAuth токен ✅» означала
«поле не пустое» и горела зелёным три недели на мёртвом токене. Спрашивай себя,
что именно проверяет зелёный цвет.

**Логи запросов неполные.** По ним нельзя судить, работал ли оверлей: часть
обращений не пишется. Отсутствие записи ≠ отсутствие обращения.

## 3-бис. Таблица соответствия по каждой платной механике

Правильная форма отчёта, а не набор разрозненных запросов. По каждому платному
действию должна сходиться цепочка:

| покупка | доставка | фактический эффект | терминальное состояние | возврат |
|---|---|---|---|---|
| списано N💎 | мод забрал | видимое изменение в игре/БД | `acked`/`failed` | если провал — вернулось РОВНО N |

Где рвётся — там и дефект:

- списано, доставки нет → зависшая заявка (2.2а);
- доставка есть, эффекта нет → тихий no-op, механика мертва (2.3);
- эффекта нет, но состояние `acked` → **ранний ACK принят за успех** — самая
  коварная строка, потому что выглядит как успешная;
- провал есть, а вернулось 0 → потеря денег (2.2б, ровно PB-01);
- терминального состояния нет вовсе → вечный `pending` (2.2в, ровно PB-02).

**Без последней колонки `acked` успехом не считается.** Это не придирка: мод
подтверждает действие ДО того, как выполнит его.

## 4. Как оформлять находки

- **Файл и строка либо запрос к базе с выводом.** Без этого — не находка.
- **Сценарий по шагам:** что делает зритель, что получает, где теряются деньги.
- **Прежде чем сказать «проверки нет» — поищи её в другом слое** (фронт, бэк,
  мод) и скажи, где искал.
- **Сортировать по цене ошибки**, не по количеству.
- **Уверенность:** ТОЧНО (видел весь путь) / ВЕРОЯТНО (часть не видел).
- Стиль и «можно красивее» — не нужны.

**Проверяющий по коду заинтересован отклонить чужую находку.** Отклонение без
доказательства не принимается: нужен тот же уровень подтверждения, что и для
самой находки.
