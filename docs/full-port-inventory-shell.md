# Legacy shell and configuration inventory for the Preact panel port

Read-only source inspection on `feature/panel-preact-full` at HEAD `b2064f4`; the shared working tree also contains uncommitted candidate edits, so references describe the source visible during this pass. This note compares the shipped shell under `Расширение/frontend/` with the candidate under `frontend-next/`. It does not claim a browser or hosted run.

## What the current boundary is

The old `extension.html` and `mobile.html` are parallel, script-tag shells. They load the shared viewer core, the game registry, Bannerlord/RimWorld/ShedColony modules, and `realtime.js`; both include the same cache-busted script versions (`Расширение/frontend/extension.html:616-646`, `Расширение/frontend/mobile.html:602-632`). `viewer.js` owns Twitch identity, shared viewer state, tabs and core polling. Game code registers start/stop hooks in `viewer-registry.js`; the core passes `active_module` into that registry after authenticated stats arrive (`Расширение/frontend/viewer.js:1101-1164`, `Расширение/frontend/viewer-registry.js:45-54,89-114`).

`frontend-next/panel-mobile.html` and `panel-extension.html` are separate Bannerlord-only entry points mounting `PanelApp` (`frontend-next/panel-mobile.html:10-12`, `frontend-next/panel-extension.html:10-12`; `frontend-next/src/panel/main.tsx:13-21`). The ordinary `frontend-next/mobile.html` and `extension.html` still mount the skill-game surface, not this panel (`frontend-next/mobile.html:10-12`, `frontend-next/extension.html:10-12`). `PanelApp` currently exposes Development, Equipment, Combat and Dynasty tabs and includes the tournament panel within Combat (`frontend-next/src/panel/PanelApp.tsx:12-15,54-58`; `frontend-next/src/panel/main.tsx:21`; `frontend-next/src/panel/TournamentPanel.tsx:14-20`). The Preact panel is therefore not yet a drop-in replacement for the old common shell: it has no core tab bar/module registry, and its page does not preserve the RimWorld/ShedColony/core areas.

Critical notice state rule: the legacy client displays a notice before it awaits ACK and does not inspect the ACK response (`viewer.js:1054-1082`). A failed ACK can repeat a toast on the next 20 s poll; a successful ACK means a page closing after the server marks it can prevent the viewer seeing it. If notices move, preserve the current per-identity scoping and decide deliberately whether acknowledgement follows visible delivery or mere fetch. Do not acknowledge notices from a stale identity callback.

## Configuration view

`Расширение/frontend/config.html` is a small Twitch config-view document; it loads the Twitch helper and `config.js` (`config.html:4-7,77-113`). It has one self-service setting: the Pets overlay toggle. On `onAuthorized`, `config.js` copies `channelId` and JWT, then GETs `/api/overlay/pets?channel_id=...`; the GET is intentionally public because OBS overlay clients lack Twitch auth. Toggling POSTs `{enabled}` to `/api/streamer/pets/overlay-toggle` with the JWT (`config.js:6-25,42-55`). The backend GET returns only the named channel's overlay state/viewers; the POST requires broadcaster role and derives channel ID from the verified JWT, ignoring a client channel field (`Расширение/backend/routes/pets.py:195-213,218-245`).

Port/security details: preserve JWT-derived channel scoping on the write. The config page's public GET is an intentional overlay API, not proof that the config view itself is authenticated. The JS does not check `response.ok` on its GET and has no callback generation fence (`config.js:19-28`); a failed GET can render a false/off toggle, and an older authorization response can repaint a newer channel's view. A stale click still sends the currently held broadcaster JWT, so the backend channel is the final authority. The separate streamer dashboard action for `active_module` is not in this config view (`Расширение/backend/routes/streamer.py:842-867`).

## Critical risks and backend/release blockers

1. **CSP origin is handled by the build; hosted output still needs release verification.** The source panel HTML template contains only the base connect list (`frontend-next/panel-mobile.html:6`, `panel-extension.html:6`), but Vite validates `VITE_SKILLGAME_EBS_ORIGIN` and injects it into all six non-tournament app pages, including both panel pages (`frontend-next/vite.config.ts:6-20`). `check-build.mjs` derives the same configured origin and asserts the emitted CSP source list exactly (`frontend-next/scripts/check-build.mjs:6-14,62-67`). Therefore the template alone is not a confirmed CSP blocker. Verify the production build uses the intended EBS origin and inspect that built artifact/Hosted Test before release; empty origin means same-origin routing by design (`src/skillgames/origin.ts:3-18`).
2. **No module gating before Bannerlord bootstrap.** Candidate startup requests game endpoints as soon as identity resolves and mounts Bannerlord-only views without first resolving `active_module` (`PanelApp.tsx:19,52-58`; `controller.ts:64-71,213-220`). Integrating this as the general shell without a host-level module decision risks showing a Bannerlord surface on non-Bannerlord channels and issuing irrelevant game reads. Existing backend contracts expose the correct channel module through viewer stats, but candidate does not use it on startup.
3. **Core shell behavior is not covered by the port.** Candidate omits `/api/viewer/online`, `/api/viewer/online-list`, `/api/viewer/perks`, `/api/notices` + ACK, activity/attendance reporting, `active_module`, and PubSub. If the old scripts are removed globally, viewer presence, badges, notices/refunds outside Bannerlord, and core mini-game/voting realtime behavior disappear (`viewer.js:463-516,925-1005,1038-1087`; `realtime.js:82-109`; subscribers above). Track each as a deliberate migration item.
4. **Legacy identity completion can race.** `viewer.js` updates `userLogin` from each async identity lookup with no request sequence/owner check (`viewer.js:416-425`). Stats reads themselves have a sequence fence (`viewer.js:1099-1116,1127-1148`), but an older resolve completing last can still set the displayed login and initiate fresh requests under the latest shared token. Keep the candidate's `IdentityBootstrap` generation/abort check when wiring shared shell behavior (`frontend-next/src/skillgames/identity.ts:32-55`).
5. **Public config is presentation only.** `/api/bannerlord/config` is intentionally unauthenticated and returns prices/UI data (`Расширение/backend/routes/bannerlord.py:1320-1360`). The backend comment says prices are not enforcement; action routes must continue validating/charging server-side. Preact does send authenticated mutation requests with client action IDs and blocks an identity after an unknown outcome (`frontend-next/src/panel/transport.ts:25-69`); do not regress this to trusting rendered prices or retrying uncertain writes.

## Suggested integration order

1. Confirm the production build resolves the intended API origin and that the emitted CSP matches it; the Vite transform and build gate already implement this contract.
2. Keep `viewer.js` as the host while adding an explicit `active_module`-driven view switch; ensure a module or identity transition stops old pollers and fences late responses before starting the new panel.
3. Inventory core shared functions one by one: presence, perks, activity/attendance, generic notices/ACK, and PubSub-dependent games. Assign each to the shared host or a new owner; do not remove the legacy script bundle until the consumers have an owner.
4. Carry over the candidate's auth generation, stale-response and uncertain-mutation protections. Treat `active_module`, login, prices, and UI disabled state as display/context only; the JWT and backend route remain the authority.
