## Endpoint, catalog, and price findings

- Preact generic mutations post `{action_type,data}` with a generated `client_action_id` to `/api/bannerlord/action` (`panel/transport.ts:44-68`). The legacy helper captures lifecycle/token, submits through `ShedLink.buyAction`, invalidates outstanding hero/vassal reads on acceptance, then refreshes after the mod queue delay (`viewer-bannerlord.js:832-864`). Keep this delayed refresh and invalidate/fence prior reads after accepted mutations.
- The tournament pilot already uses the typed tournament transport and endpoint, but no panel controller owns it. `GET /api/bannerlord/tournament` returns queue entries (`username`, `entry_fee`, `class_key`), state/participants/current round, `in_queue`, `my_prediction`, `my_username`, and config `{entry_fee_gold,join_price}` (`backend/routes/bannerlord.py:661-746`). The separate config endpoint also returns `tournament_prize_gold` and `tournament_round_gold` (`:1331-1348`); these values are not in the tournament snapshot type/pilot request sequence, so ported prize text needs the config request or should be omitted. Legacy displays `/16` (`viewer-bannerlord.js:1144-1152`); the actual queue size constant is mod-side `TOURNAMENT_SIZE = 16` (`BannerlordLink/src/Behaviors/TournamentQueueBehavior.cs:40`), and neither the tournament response nor config exposes that capacity. Backend action guards running state, already-queued, and pending duplicate join (`backend/routes/bannerlord.py:2967-3009`); the mod decides whether its queue has room. Treat capacity as an unexposed game limit, not a backend-provided field. `combat.ts` deliberately strips tournament from combat order, so integrate the pilot or route it as a panel tab.
- `/api/bannerlord/config` is a settings payload, not a universal catalog. It returns `ui`, give-gold/add-skill presets, focus costs, attribute cost, recruitment tier costs/multiplier, gear costs, reforge/spawn prices, gender/baby costs, workshop/caravan prices, tournament prize/round display values, `action_prices`, `power_prices`, and `hero_gold_costs` (`backend/routes/bannerlord.py:1320-1375`). The `ui` member is presentation only (`backend/modules/bannerlord/ui_config.py:1-5,12-20`). It omits culture ids, workshop type ids, settlement ids, child/vassal entity lists, and shop catalog entries; those come from whitelists, specialized reads, or `/api/bannerlord/shop` as detailed above. Several prices have separate shapes: crustic/action quote map vs hero-gold cost map vs specialized shop/tournament fields. Legacy `_bnrPrice`/`_bnrGold` can fall back for display (`viewer-bannerlord.js:956-969`), but mutation controls should require the relevant authoritative field.
- Backend actions exist, but that does not prove a selector/catalog is exposed. The routes whitelist Bannerlord actions (`backend/routes/bannerlord.py:934-1017`) and the manifest declares them (`backend/modules/bannerlord/manifest.yaml:108-198`); dynamic ids and caps must be checked separately. Confirmed exposed catalogs: equipment/build snapshots, shop `module_catalogs`, settlement list, owned workshops plus `max_workshops`, owned party/fief/caravan snapshots, children/proposals, and eligible heirs. Confirmed non-catalog controls: culture whitelist is duplicated in frontend/backend; workshop type ids are hardcoded in frontend and there is no live type catalog endpoint. Treat those as explicit catalog/contract gaps, not completed backend parity.
- Do not confuse `family.js` platform marriage routes with Bannerlord hero marriage actions. The former has its own `/api/marriage/*` read/write flow and `divorce_cost`; the latter goes through the Bannerlord action endpoint and game-hero prices/cooldowns.

## Stale-slot and identity risks to preserve

Legacy `innerHTML` subslots are rebuilt during hero rendering. Its sub-loaders rerun after render and event handlers bind only when the pane DOM actually changes (`viewer-bannerlord.js:5879-5906`); careless manual slot reuse can leave old controls/listeners attached. Accepted actions invalidate old hero/vassal reads and perform a delayed refresh (`:848-861`).

The Preact controller already has generation, token, and owner checks for party/diplomacy reads and mutations (`panel/controller.ts:132-163,168-189`), and clears state/aborts requests on identity invalidation (`:32`). New child, proposal, vassal, shop, and social-family flows need the same ownership discipline: capture channel/user/hero/entity with the request, ignore late replies after identity/hero changes, and re-check current entity/quote before submit. Do not key a mutation only by a stale DOM row or cached inventory slot. The existing equipment controller similarly filters ambiguous slot-only reads to the active hero (`LESSONS.md:1-11`).
