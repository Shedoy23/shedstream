## Найденное на исходной точке

1. **HIGH: вечная блокировка генерации после смерти процесса.** `skillgames/service.py:413–417` считает все строки `status='generating'`, включая просроченные и принадлежащие мёртвому runtime. `_expire` вызывается лишь для текущего игрока/выбранного соперника. Две брошенные генерации блокируют новые открытия всем новым зрителям канала. Воспроизведение: две admitted-строки generating с истёкшим expires_at и dead lease; новый экземпляр сервиса и Charlie начинают новую партию; open возвращает 503 generation_busy; старые две строки остаются навсегда без возвращения старых игроков. Нужна ограниченная очистка до проверки admission.

2. **MEDIUM: ошибочная обработка 403/429.** `routes/skillgames.py:107` перехватывает FastAPI HTTPException из require_jwt_user общим except и превращает законные отказ авторизации/лимит в 503 service_unavailable. Теряется причина, статус и Retry-After. Воспроизведены оба статуса. Нужен пропуск HTTPException до generic handler.

3. **MEDIUM: неограниченное накопление квитанций.** `skillgames/service.py:214–219,357–387` сохраняет каждую успешную no-op отмену очереди с новым request_id. Индекс retention есть, удаления нет. 100 no-op отмен дали 100 постоянных записей. Общий каналовый rate-limit ограничивает скорость, но не накопление; нельзя удалять свежую квитанцию без опубликованного окна безопасного retry. Дополнительно история игроков не имеет полноценного индекса `(channel_id,username)`, а старые приватные boards/certificates не имеют политики хранения. Durable result ledger требуется сохранить.

4. **MEDIUM: соперник стирает ручную расстановку.** `frontend-next/src/skillgames/SkillgameView.tsx:33` сбрасывает локальный draft при любом общем session.version. `place/autoplace/ready` соперника повышает эту версию; следующий poll стирает ещё не отправленные корабли моего игрока, хотя own_ships не менялись. Независимый DOM-тест выбрал A1, затем получил opponent_ready=true/version1: A1 перестал быть кораблём; vitest exit 1. Нужна синхронизация по session id и собственной серверной расстановке, а не общей версии.

5. **MEDIUM: зависимость Pydantic v2 не объявлена.** Новый route требует model_validator и model_validate_json, но requirements содержит лишь fastapi==0.104.1; его package metadata допускает Pydantic >=1.7.4,<3. Окружение с v1 по-прежнему удовлетворяет требованиям, но импорт нового router при startup падает. Тестовый venv использует 2.13.5 и этот случай не обнаруживает. Нужна явная совместимая v2-зависимость или совместимая реализация валидации.

## Проверенные границы, а не универсальная гарантия

- Public projections используют явные списки полей; mines/seed/proof и чужой флот не выдаются, включая конец игры. Own ships допустимы для владельца
- Membership + channel берутся из проверенного JWT; body не задаёт username/channel/result/score. Чужой session id возвращает 404. SQL параметризован
- BEGIN IMMEDIATE объединяет ход, проверку версии, receipt, итог и изменения рейтинга. Ключ результата per(channel,session) защищает от второго начисления; old games не используют новые session tables
- Начальная область сапёра безопасна; сертификат использует открытые числа и известное общее число мин. Advanced требует вычитания вложенных ограничений; простые или несертифицированные поля не принимаются. Это доказательство решаемости, не доказательство отсутствия внешнего бота у игрока
- CPU-генерация ограничена числом попыток, wall-time и работой, выполняется вне SQLite writer transaction. Сценарий stale admission показал, почему наличие лимита само по себе недостаточно
- Денежный результат новых игр равен нулю; отдельная ветка новых сезонов не вызывает старые выплаты. Калибровка сложности/баланса не заявляется
