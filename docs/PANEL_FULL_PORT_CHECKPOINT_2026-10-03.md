## Конкретное противоречие требований, требующее решения владельца

Полный перенос каждой старой кнопки несовместим с запретом переносить клиентские каталоги при текущем API:

1. **Выбор культуры создаваемого героя.** Старый UI содержит фиксированные culture IDs (`viewer-bannerlord.js:5411–5455`), backend проверяет свой фиксированный whitelist (`routes/bannerlord.py:1941–1952`). `/api/bannerlord/config` не возвращает каталог культур. Выводить все допустимые культуры из случайного списка поселений нельзя: это другой набор сущностей, он может быть неполным.
2. **Тип покупаемой мастерской.** `_BNR_WORKSHOP_TYPES` содержит 11 клиентских ID (`viewer-bannerlord.js:1388–1400`). `/api/bannerlord/my-workshops` возвращает только уже принадлежащие мастерские и лимит; `/api/bannerlord/settlements?type=town` возвращает города, не типы мастерских. Упомянутый в docstring `/api/bannerlord/workshop-towns` фактически не зарегистрирован. Мод разрешает тип через runtime `WorkshopType`, но не отдаёт этот каталог панели (`WorkshopHandlers.cs:119–127,214–255`).

Проверены все `.py`/`.yaml` backend вне тестов **на принятой базе b2064f4**; альтернативного каталога не найдено. Это не утверждение об отсутствии функции во всех ветках. Родитель отдельно сообщил о более новом контракте `GET /api/bannerlord/content-catalogs` в `progression` на `cd125a5` (cultures/policies/skills/attributes, identity-scoped ingestion и hero.create по cultures); точные anchors родитель ещё проверяет. Следовательно, культура — рассинхронизация принятой базы с существующей новой реализацией. Workshop types, по той же проверке родителя, отсутствуют даже в новом CATALOG_TYPES. Ни новый endpoint, ни хардкод в обход плана не добавлены; backend из progression не переносился.

**Нужно решение владельца о согласовании культуры с новым контрактом progression, а для мастерских — отдельный серверный/модовый контракт типов либо явное исключение выбора типа.** Это блокирует именно указанные выборы. Независимые разделы продолжаются; остальные неготовые разделы ниже не объявляются зависимыми от этих API. Документ обновляется по мере завершения срезов и пока не является финальной сдачей.

## Что доказано и где граница

- Турнирный oracle выполняет неизменённые legacy scripts в реальном jsdom/VM; настоящие event handlers, сетевой fetch recorder и управляемые timers. Сравниваются все запросы выбранного host, включая telemetry, отказы, 3-секундный poll, 3,5-секундный хвост и скрытую страницу. Это **selected-host parity**, не запуск всей старой оболочки. Полный startup parity остаётся невыполненным.
- Config oracle выполняет неизменённый старый `config.js`, нажимает реальную кнопку, сравнивает method/path/query/raw body/JWT/content-type с Preact. Сетевые вызовы направлены только в fixtures.
- Сгенерированные client_action_id/batch_id нормализуются. Форжевое `expected_item_id` остаётся единственным принятым отличием wire. Новые payload/URL не добавлены.
- UI-отличия описаны в коммитах и тестах: отсутствие серверной join quote больше не подменяется нулём; подтверждение прогноза закрывается при наблюдаемой смене турнира/раунда; config не применяет поздний ответ старого канала и не считает malformed response выключенным состоянием.
- Невидимая смена турнира между GET и POST без server-side tournament ID **не решена**. Запрос не получает выдуманный ID. Это отдельный контрактный риск.
- Новый турнир показывает заявки как отложенный исход, использует реальные серверные призовые значения без fallback, не копирует предел очереди 16 и число раундов 4 из старого UI.
- Фокус подтверждения направлен на отмену, Escape закрывает окно, Tab удерживается внутри. Unknown server refusal показывается текстом сервера.
- Подключённый Chromium `145.0.7632.6`: localhost+клик проверены; финальный fixture-прогон 1280×900 и 375×900, 14 снимков, 0 page errors, 0 непредусмотренных внешних запросов. Browser sandbox включён, `bypassCSP` не применялся. Twitch Helper заменён тестовым ответом только в browser route; это не обход CSP и не настоящее Twitch подтверждение.
- На 375px реально поймано исходное переполнение до 404px; вкладки переведены на перенос. Сохранены `initial-overflow.json` и снимок `combat-375-before.png`; финальный прогон переполнения не обнаружил.

## Найденные дефекты старого UI/серверные ограничения (не исправлялись)

1. Отсутствуют серверные каталоги культур/типов мастерских; старый frontend держит ID у себя.
2. В старом турнире есть выдуманные display fallback prizes/capacity/round count. В новом турнире fallback не копируются.
3. Prediction storage не имеет надёжной привязки к уникальному турниру; прежний прогноз раунда 0 может пережить завершение. Невидимую смену между GET/POST клиент не закрывает (`DEFERRED.md`, прежний `FRONTEND_PILOT_2026-10-02.md`).
4. Старый config может применить поздний ответ прежнего канала и принимает любой truthy/falsy `enabled` без `response.ok`/shape проверки. Старый файл сохранён.
5. Pet unequip адресует slot без expected-item. Разбор других устаревших targets (дети, вассалы, workshop/colony coordinates) — в inventories; не объявляется решённым.
6. RimWorld dedicated paid endpoints, daily-claim и clan-upgrades/buy не имеют долговечного client_action_id контракта. Новый выдуманный ключ не добавлялся.
7. Notices/ACK и active_module ещё не перенесены. Нельзя подключать этот checkpoint как единственную Twitch-панель: иначе исчезнут неготовые функции.
