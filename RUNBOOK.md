## 1. Главный принцип: доказательство вместо рапорта

**Успех подтверждается внешним признаком, а не сообщением исполнителя.**

За один день 2026-07-22 этот класс ошибки всплыл четыре раза:

| Что рапортовало | Что было на самом деле |
|---|---|
| Mass Upgrade: «нужен перезапуск» (подразумевая «сохранил») | не сохранял ни у кого с мая |
| Загрузчик Workshop: `Finished...` | не опубликовал ничего |
| Мод RimWorld: команда поставлена в очередь | очередь молча теряла все строки с миграции m1 |
| Расширение: «закон на голосовании» | закон давно принят, статус не обновлял никто |

Отсюда правило на каждую проверку: не «сервис пишет ок», а **запрос в боевую базу /
дата на странице / строка в логе игры / вывод теста**. Ниже под каждую подсистему
дана конкретная такая проверка.

## 4. Бэкапы и восстановление

**Три независимых механизма, все проверены 2026-07-22 — рабочие.**

| # | Кто | Куда | Формат | Хранит |
|---|---|---|---|---|
| 1 | cron 05:00, `backup_db.sh` | `/root/twitch-extension/backups/viewers.daily.*.db.zst` | сжатые ~8.8 МБ | 15 дневных + 7 недельных |
| 2 | in-process `backup_loop.py` | `/root/twitch-extension/backend/backups/backup_*.db` | **несжатые 65 МБ** | ~15 штук = 910 МБ |
| 3 | **офсайт** | `%USERPROFILE%\shedstream-backups\` на ПК владельца | сжатые | 18 копий (сверено 2026-07-27, задача LastTaskResult=0) |

### Офсайт устроен как ЗАБОР, а не отправка

Задача Windows **`shedstream-db-backup-pull`** (ежедневно 13:00,
`scripts/pull-backup.ps1`) тянет свежий `.zst` с прода на локальный компьютер.

**Искать офсайт grep'ом по серверу бесполезно — его там нет и быть не должно.**
2026-07-22 я на этом ошибочно объявил дыру; владелец поправил.

Проверка:
```powershell
Get-ScheduledTaskInfo -TaskName "shedstream-db-backup-pull"   # LastTaskResult должен быть 0
Get-ChildItem "$env:USERPROFILE\shedstream-backups" | Sort-Object LastWriteTime -Desc | Select -First 3
```

### Как доказать, что бэкап рабочий (а не просто лежит)

**Проще всего — одной командой, с ПК владельца:**
```bash
python scripts/verify-backup.py        # свежий срез;  --all = все 14
```
Разжимает, гоняет `integrity_check`, проверяет что `viewers` не пуста.
Коды выхода: **0** восстановим · **1** битый, разбираться сейчас ·
**2** проверить не вышло (нет пакета `zstandard`) — это НЕ «бэкап плохой».
Разводить 1 и 2 обязательно: ежедневная ложная тревога приучает не смотреть
в лог, и тогда настоящую поломку тоже пропустят.

**Запускается само:** с 2026-07-25 `pull-backup.ps1` вызывает эту проверку
после каждого забора и пишет результат в `pull-backup.log` строкой
`verify: restorable` / `VERIFY FAILED` / `verify: SKIPPED`. До этого
единственной проверкой было «файл больше 1024 байт» — её проходит и архив,
скачанный наполовину. Разовый дрилл 2026-06-13 доказал восстановимость той
копии, но ничего не говорил про скачанную сегодня.

**Вручную, на сервере:**
```bash
# на сервере, где есть zstd
zstd -d -q -f /root/twitch-extension/backups/viewers.daily.YYYY-MM-DD.db.zst -o /tmp/rc.db
python3 -c "
import sqlite3; c=sqlite3.connect('/tmp/rc.db')
print(c.execute('pragma integrity_check').fetchone()[0])
print('зрителей:', c.execute('select count(*) from viewers').fetchone()[0])"
rm -f /tmp/rc.db
```
Плюс сверить MD5 локальной копии с серверной — докажет, что перенос не исказил файл.

Результат теста 2026-07-22: `integrity_check: ok`, 106 таблиц, 76 зрителей,
5 731 423 очков, 22 героя. MD5 совпал.

### Ключ подписи релизов — резерв (2026-08-22)

Приватный ключ `shedlink-release-2026` подписывает манифесты установки. Если он
пропадёт, **старые релизы останутся валидными, но новый подписать будет нечем**:
уже установленные Manager'ы перестанут принимать обновления, и лечится это
только выпуском нового ключа и новой сборки для всех.

До 22.08 копия была ровно одна — `%LOCALAPPDATA%\ShedLink
elease-keys\`, на
системном NVMe. Это опасно вдвойне: та же папка хранит состояние Manager, и
любая чистка «снесём ShedLink» уносит ключ вместе с мусором.

| Где | Диск | Что там |
|---|---|---|
| `%LOCALAPPDATA%\ShedLink
elease-keys\` | disk 1, NVMe (C:) | рабочая копия |
| `D:\shedlink-release-keys\` | **disk 0, отдельный HDD** | резерв, доступ только у владельца |

**Как убедиться, что резерв рабочий** (не «файл лежит», а «им можно подписать»):
из копии выводится публичный ключ, его отпечаток обязан совпасть с зашитым в
Manager `17e6043cca11dcb9f4230d5a91325e9d5d52ba9a29bb4cc4a6ffb51618001541`.

```bash
python -c "
from cryptography.hazmat.primitives import serialization; import hashlib
k = serialization.load_pem_private_key(open('D:/shedlink-release-keys/shedlink-release-2026.private.pem','rb').read(), password=None)
pub = k.public_key().public_bytes(serialization.Encoding.DER, serialization.PublicFormat.SubjectPublicKeyInfo)
print(hashlib.sha256(pub).hexdigest())"
```

**Чего этот резерв НЕ закрывает:** обе копии в одной квартире. Настоящий офсайт
(флешка в другом месте либо менеджер паролей) — ручной шаг владельца, машина его
сделать не может. Ключ в git не кладём никогда.

## 5. Деплой

```powershell
pwsh scripts/deploy.ps1 -Backend     # только сервер
pwsh scripts/deploy.ps1 -Mod         # сборка + копия DLL в игру + сверка md5
pwsh scripts/deploy.ps1 -All         # мод + бэк + фронт
pwsh scripts/deploy.ps1 -DryRun      # ничего не менять, показать план
```

Если `pwsh` не найден: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\deploy.ps1 -Backend`.

**Что делает сам:** прогоняет критические тесты (красный тест = деплой не пойдёт),
тарит без `*.db`/`.env`, рестартит supervisor, проверяет `RUNNING` + `/health` 200.

Для миграционного deploy сначала создаётся консистентная SQLite-копия через
`ops/production/create_predeploy_backup.py`, а после перезапуска база проверяется
read-only скриптом `ops/production/postdeploy_db_audit.py`. Архив недостаточно
просто создать: offsite-копия должна совпасть по SHA-256 и реально восстановиться
через `scripts/verify-backup.py`.

**Правила:**
- `deploy.ps1 -Frontend` обновляет наш сервер, но **не обновляет публичный
  Twitch CDN-фронт**. Публичный фронт выпускается только новой версией через
  `Расширение/docs/TWITCH_UPDATE_RELEASE_PLAYBOOK.md`;
- пока новая версия в Review, submitted ZIP неизменяем; backend-деплой обязан
  оставаться совместимым и с текущей Released-, и с новой submitted-версией;
- перед `-Mod` **закрыть игру** — иначе DLL занят;
- прод-деплой во время стрима — только хотфикс падающего.

RimWorld можно отдельно открыть для технических viewer-action прогонов без
активного Twitch-эфира через `RIMWORLD_REQUIRE_STREAM_LIVE=false` в production
`.env`. Не использовать для этого `TESTING_BYPASS_STREAM_LIVE=true`: общий флаг
снимает gate также с дуэлей, TTS и других модулей. Возврат безопасного поведения:
поставить RimWorld-флаг в `true` и перезапустить `twitchbot`.

**Безвредный транзиент:** `tar: timestamp … in the future` — локальные часы впереди
серверных, файлы уже распакованы. Проверить curl'ом и жить дальше.

### Как доказать, что EventSub реально доставляет события (2026-08-22)

Расследование «бот не приветствует фолловеров» заняло час только потому, что
каждый быстрый индикатор здесь врёт. Порядок проверки — от самого надёжного:

1. **nginx — единственный честный свидетель доставки.** Приложение может
   отбросить событие молча, Twitch может не прислать его вовсе; nginx видит сам
   HTTP-запрос. День лежит в своём архиве (ротация суточная):
   `zcat /var/log/nginx/access.log.N.gz | grep eventsub`.
2. **Что Twitch думает о подписках** — статус, условие и дату создания:
   `GET https://api.twitch.tv/helix/eventsub/subscriptions` с app-токеном.
   `enabled` означает «Twitch не считает подписку сломанной», а НЕ «доставка идёт».
3. **Помечает ли обработчик свою работу в логе.** Часть типов обрабатывается
   молча (`channel.chat.notification` без watch_streak, приветствие при
   выключенной настройке) — отсутствие строки не значит отсутствие события.

**Ловушки, на которых я сам обжёгся в этом расследовании:**

- `eventsub_seen` — таблица ДЕДУПА с TTL 24 часа, а не журнал. Пустая таблица
  значит «сутки не было событий», а не «событий не было никогда».
- OAuth-токены в базе **зашифрованы** (Fernet, `DB_ENCRYPTION_KEY`). Отправив
  значение из базы напрямую в Twitch, получишь 401 и решишь, что токен мёртв.
  Расшифровывать через `database._decrypt_secret`, интерпретатором
  `/root/twitch-extension/venv/bin/python` (в системном нет aiosqlite).
- `zcat /var/log/nginx/access.log.*.gz` отдаёт файлы в лексикографическом
  порядке (`.10` раньше `.2`), поэтому `tail` показывает НЕ последнее по
  времени. Фильтровать по дате явно.
- Сервер живёт в **UTC**, `followed_at` у Twitch тоже UTC — но перед сверкой
  это надо подтвердить (`date`), а не предположить.
- Стрим-сессию может создать и опрос-фолбэк в боте, и EventSub. Наличие сессии
  НЕ доказывает, что webhook работает — доказывает строка `rimlink.eventsub:
  🔴 stream.online`.
- Проверять надо и обратную связь: после `stream.online` настоящий `event.id`
  обязан попасть в память polling-loop до установки live-cache. Иначе кэш на
  300 секунд запрещает Helix-запрос, polling создаёт сессию под датой, а после
  TTL переключается на Twitch id. На проде 06.09 это снова дало две сессии;
  машинная проверка — `backend/tests/test_stream_session_single.py`.

**Чем сверить, что события не теряются:** число фолловеров у Twitch
(`GET /helix/channels/followers`, поле `total` и даты) против строк
`follow-greet` в логе. Расхождение = доставка встала.

**Проверено 2026-09-01 по эфиру 28.08: доставка `channel.follow` жива.**
Разбивка принятых событий за день — одной командой:

```bash
ssh root@31.130.132.224 "grep -h 'eventsub: принято type=' /var/log/twitchbot.out.log | sed -E 's/^([0-9-]+).*type=([a-z_.]+).*/ /' | sort | uniq -c"
```

28.08 дала `1 channel.follow`, `2 stream.online`, `2 stream.offline`,
`46 channel.chat.notification`, и рядом в логе — `👋 follow-greet`. То есть
пересоздание подписки 22.08 действительно починило доставку. **Чего эта команда
НЕ доказывает:** рейдов и битов в тот день не приходило вовсе, и ноль здесь
значит «никто не рейдил», а не «рейды сломаны» (`CLAUDE.md`, «Один признак —
один смысл»).

### День второго арендатора — как проверять первого чужого стримера

Задумано 2026-08-22, после того как за день нашлось три дефекта вида «одно на
всю платформу там, где должно быть по числу каналов». Все три были невидимы,
пока канал один: платформа и проект-под-одного при одном стримере
неразличимы в наблюдении.

**Чего НЕ делать:** сидеть весь эфир и «периодически всё чекать». Время
владельца дороже машинного, а глазами такие дефекты как раз и не ловятся.

| Кто | Что снимает |
|---|---|
| скрипт (написать, когда человек будет известен) | не легли ли данные чужого канала под `channel_id` владельца и наоборот; строки `channel-default:` в логе; что бот писал в его чат |
| воронка онбординга | путь новичка сам: скачал → поставил → вошёл → готов, и где встал |
| владелец | двадцать минут смотрит его стрим как обычный зритель |
| **сам стример** | «бот написал какую-то дичь» — самый ценный сигнал, он один не знает, как «должно быть» |

**Что смотреть в первую очередь** (по следам находок 22.08): автосообщения в
его чате — точно ЕГО, а не владельца; анонс его эфира не улетел в Telegram
владельца; объявления мини-игр пришли в его чат, а не в чужой.

После прогона: строки `channel-default:` из лога — это рабочий список того,
что чинить; каждая называет файл и номер строки.

### Проверка фронта на несуществующие вызовы (eslint no-undef, 2026-08-23)

Ловит класс, который убил магазин RimWorld на месяцы: функцию переименовали в
одном файле, вызов остался в другом, `ReferenceError` молчит внутри обработчика
клика.

```bash
npm run lint:js
```

Гоняется сам в pre-commit, но **только если в коммите есть js фронта** — чтобы
не тормозить остальные коммиты. Проверено блокировкой: подложенный баг даёт
`[pre-commit] BLOCKED`.

**Как это устроено и где ловушка.** Файлы фронта делят одну глобальную область,
поэтому список общих имён собирается на лету из тех файлов, что подключены в
`extension.html` (`scripts/frontend-globals.mjs`). Хранить копию списка нельзя:
переименованная функция осталась бы «объявленной», и правило молча перестало бы
работать.

**Если правило вдруг сыплет ошибками на настоящих функциях** — сломан не код, а
сборщик имён. Сначала:

```bash
node scripts/frontend-globals.mjs --self-test
```

Он падает с кодом 1 и называет ненайденные контрольные имена. Чинить сборщик,
а не отключать правило.

**Новый способ объявления** (например `globalThis.X = ...` или что-то экзотичное)
надо добавить в `DECL` в сборщике, иначе имя будет считаться необъявленным.

### «Service NOT running» после деплоя может означать, что упал SSH, а не сервис (2026-09-09)

Связь до прода с этой машины периодически рвётся:

Состояние «код распакован, сервис не перезапущен» само по себе безопасно и
устойчиво: работает прежняя версия, пока её не перезапустят.

### Manager ставит МОДЫ ИЗ СВОЕЙ СБОРКИ, а не свежие (замечено 2026-09-06)

Менеджер ставит по манифестам `manifests/installation/<игра>-<версия>.json`,
вшитым в его пакет при сборке. Новый мод сам собой к пользователю не поедет:
нужен релизный ZIP в `/srv/shedlink/releases/`, манифест с его sha256 и
**пересборка менеджера**. 06.09 обнаружилось, что alpha.15 ставила ShedColony
0.1.1 и моды 0.1.2 — работу двух дней пользователь бы просто не получил, а по
номерам версий это выглядело нормально.

Проверять надо СОДЕРЖИМЫМ: скачать опубликованный ZIP и поискать в бинарнике
метку правки (например `RimLinkLog`, `PostPartial`, `SafeWage`,
`/api/shedcolony/config?full=1`). Имя файла и номер версии не доказывают ничего
— это тот же класс, что и «отгружаемый бинарник сверять с исходником».

Порядок выпуска: `pack-<игра>-release.ps1` → манифест (sha256) → **дописать
манифест в обязательный список в `scripts/package-manager-alpha.ps1`** →
`package-manager-alpha.ps1 -Version 0.1.0-alpha.N` → scp в
`/srv/shedlink/releases/` → поменять `MANAGER_RELEASE_VERSION` в
`routes/streamer.py` → деплой бэкенда → скачать обратно и сверить.
Список в упаковщике не формальность: `shedcolony-0.1.2` не попал в alpha.15
именно потому, что список его не требовал, а сборка случилась за пару часов до
появления файла.

### Резать лог бэкенда по дате нельзя — половина строк без времени (2026-09-05)

`awk '$0>="2026-09-05 12:40"' /var/log/twitchbot.out.log` **не выделяет окно
эфира**: строки, напечатанные через `print()`, метки времени не имеют и
начинаются с `[auth]`, `INFO:`, `✅`, `📥`. Все эти символы лексикографически
больше цифры «2», поэтому такая «фильтрация» пропускает весь файл — а в нём
лежат ещё и прошлые сутки. В вечернем триаже 05.09 это дало **1180**
`ExpiredSignatureError` вместо настоящих **34** и заодно раздуло счётчики
HTTP-путей.

Правильно — резать по номеру строки:

```bash
START=$(grep -n '^2026-09-05 12:4' /var/log/twitchbot.out.log | head -1 | cut -d: -f1)
awk -v s=$START 'NR>=s' /var/log/twitchbot.out.log > /tmp/evening.log
```

Проверка «я не ошибся окном»: число `[rimworld ACK ok]` + `ACK FAIL` в срезе
обязано сойтись с `count(*)` по `module_actions` за то же окно.

### Лог мода RimWorld обрывается по лимиту сообщений движка (2026-09-05)

RimWorld перестаёт писать в `Player.log` после `Reached max messages limit.
Stopping logging to avoid spam.` — и дальше молчит уже наш мод. 05.09 лимит
выбрал чужой `AutoPriorities` (4144 исключения за сессию), из-за чего в логе
осталось 298 команд из 630; выглядело это как «212 команд доставлены, но не

### Время без пометки: одна запись — две разные поломки
Найдено 2026-08-05 по жалобе «не работает таймер автоокончания голосования».
Срок писался как `datetime.utcnow().isoformat()` — **голый UTC без часового
пояса и через «T»**. Дальше его прочитали два потребителя, каждый по-своему:

- **Сервер** сравнивал `ends_at <= CURRENT_TIMESTAMP` — это сравнение ДВУХ
  СТРОК. Слева `2026-08-05T09:00:00`, справа `2026-08-05 11:49:19`. Внутри
  одной даты «T» (0x54) больше пробела (0x20), поэтому истёкшее сегодня
  голосование не находилось вообще: автозакрытие срабатывало только после
  смены даты по UTC, то есть после полуночи.
- **Браузер зрителя** делал `new Date("2026-08-05T09:00:00")`. Строка без
  пояса читается как МЕСТНОЕ время: зритель из Москвы получал срок на три часа
  раньше, и отсчёт показывал `00:00` с первой секунды.

**Как ловить:** любое сравнение времени в SQL — через `datetime(...)` с обеих
сторон, иначе это сравнение символов, а не моментов. Любое время, уходящее в
браузер, — с явной пометкой пояса (`Z`). Проверка одной строкой:
```bash
sqlite3 viewers.db "SELECT ('2026-08-05T09:00:00' <= CURRENT_TIMESTAMP), (datetime('2026-08-05T09:00:00') <= datetime('now'));"
```
Разные числа в ответе = ловушка живая. Тест: `tests/test_voting_timer.py`.

**Чинить такое — на бэкенде.** Отсчёт можно было поправить и во фронте, но
фронт замерзает на CDN до следующего ревью Twitch, а бэкенд доезжает за минуты:
пометка `Z` на сервере чинит и уже опубликованный клиент 0.0.1.

### `DEV_MODE` + `RIMLINK_ENV` — обход входа, который держится на отсутствии

`auth.py` умеет выдавать `role=broadcaster` **без токена вообще**. Условий три,
и все должны совпасть: `DEV_MODE=true`, `RIMLINK_ENV` ∈ {`dev`,`development`,
`local`}, и запрос «с localhost».

**Чем это опасно.** `RIMLINK_ENV` не встречается больше НИГДЕ: ни в
`.env.example`, ни в скриптах деплоя, ни в этом файле до сегодня. То есть на
проде обход выключен не потому, что кто-то это настроил, а потому, что
переменную никто никогда не выставлял. Второй гейт (localhost) слабее, чем
кажется: uvicorn запускается без явного `forwarded_allow_ips`, а за nginx
`request.client.host` — это то, что даст цепочка прокси, и на неё влияет
заголовок `X-Forwarded-For` от клиента.

**Правило:** `RIMLINK_ENV` НЕ выставлять нигде, кроме локальной машины
разработчика. Если понадобился dev-режим на staging — сначала убедиться, что
staging не смотрит в интернет. При сомнении проверить на проде:

```bash

```

### Тест печатает «OK» и висит — закрывай пул соединений

Симптом: тест печатает `PASSED: N FAILED: 0` или `OK` и **не выходит**. Хуже
падения: кода возврата не наступает вообще, деплой-гейт ждёт бесконечно,
красного никто не видит, а человек читает `OK` и считает тест пройденным.

Причина: пул соединений держит потоки, которые интерпретатор обязан дождаться
перед выходом (`asyncio.run` не закроет цикл, пока живы фоновые соединения).
Прод закрывает пул сам на shutdown, тестам этого никто не делал.

Лечение — в конце теста, в `finally`:
```python
if getattr(db, "_pool", None):
    await db._pool.close()
```
**У каждого `Database` СВОЙ пул.** Глобальный `close_db_pool()` тут ни при чём:
замер показал 2 потока до него и 2 после, а после `db._pool.close()` — ноль.

Проверять по факту выхода, а не по тексту:
```bash
timeout 90 python tests/X.py > out.txt 2>&1; echo $?   # 124 = висит
```
```powershell
$p = Start-Process python -ArgumentList "tests/X.py" -PassThru -NoNewWindow
$p | Wait-Process -Timeout 120 -ErrorAction SilentlyContinue
if (-not $p.HasExited) { "HUNG"; $p.Kill() } else { "exit=" + $p.ExitCode }
```
Обе оболочки не для красоты: в PowerShell 5.1 нет `timeout` из coreutils, а
`timeout 90 python ... | grep PASSED` вернёт 0 от grep даже у повисшего теста —
на этом однажды едва не отрапортован успех.

### ACK мод-действия не доказывает выполнение

**Переписано 2026-09-06: прежняя формулировка протухла.** Здесь стояло
«`ActionPoller` подтверждает `success=true` до реальной работы» — сегодня это
неверно ни для одного мода. RimWorld шлёт ACK после `command.Execute()`
(`CommandQueue.cs:419-423`), Bannerlord — после возврата обработчика
(`ActionPoller.cs:285-289`, через `MainThreadDispatcher.ExecuteTrackedAsync`).
Утверждение осталось от времени до MOD_CONTRACT и успело уехать в ROADMAP как
основание для отдельной задачи.

**Чем ACK опасен на самом деле:** успех — значение по умолчанию.
`MainThreadDispatcher.FinishHandler` меняет исход только когда обработчик сам
сказал «неуспех», поэтому путь, забывший назвать исход, подтверждается как
успешный — даже если в игре ничего не произошло. Поэтому судить об исходе по
`module_actions` по-прежнему нельзя: нужен наблюдаемый эффект (строка в
доменной таблице, отметка в логе мода, изменение состояния героя).

**И даже `error_msg` в `module_actions` нельзя считать полным журналом
отказов.** На стриме 28.07 мод отправил 20 `action.failed`, а в БД осталось
19 строк с ошибкой: поздний ACK одной из них стёр `REFUNDED:` и записал
`error_msg=NULL`. В постстрим-триаже сравнивать число `action.failed` в
мод-логе с числом отказов в БД и разбирать каждый diff по `action_id`.
Живой случай и запросы:
`Расширение/docs/POSTSTREAM_TRIAGE_2026-07-28.md`, PT-28-01.

### Manager, запущенный ПРЯМО ИЗ ОКНА АРХИВА, врёт «каталог повреждён» (2026-08-28)

**Что видно:** «Release-каталог Manager недоступен или повреждён», кнопка
«Установить» не работает.
**Что на самом деле:** программу запустили двойным кликом по `.exe` внутри
архиватора (у нас — 360zip). Архиватор распаковывает во временную папку
ТОЛЬКО сам `.exe`, а `ReleaseConfiguration.TryLoadReleases` ищет папку
`Release\` рядом с исполняемым файлом. Её там нет →
`DirectoryNotFoundException` → общий catch → сообщение про «повреждён».
Каталог при этом целый.
**Как отличить за 10 секунд:**

```powershell
Get-Process ShedLink.Manager.App | Select-Object -ExpandProperty Path
```

Путь вида `C:\Windows\Tempðzip$Temp\...` (или любой `%TEMP%`) — это оно.
В нормально распакованной папке рядом с `.exe` лежат `Release\`, `RELEASE.json`
и `START-HERE.txt`; во временной — один файл.
**Починка:** закрыть Manager, распаковать ZIP целиком в отдельную папку,
запускать оттуда. Про это написано в `START-HERE.txt` пунктом 1 — текст в
файле от ошибки не защищает, сообщение программы обязано называть причину само
(записано в `DEFERRED.md`).

### Архив мода Bannerlord собирать ТОЛЬКО по списку файлов

У RimLink секрет лежит вне папки мода (`LocalLow`), поэтому упаковщик физически
не может его захватить. У Bannerlord секрет лежит ВНУТРИ папки мода:
`Modules/Shedoy23.BannerlordLink/config.json` содержит `module_token` и
`channel_id`, и Manager с 16.08 пишет туда настоящий рабочий токен.

Отсюда правило: `scripts/pack-rimlink-release.ps1` перечисляет файлы явным
списком и падает, если файла нет. Упаковка «взять папку целиком» отправит токен
владельца каждому, кто скачает архив, — и заметить это по самому архиву нельзя,
он выглядит нормальным.

`scripts/pack-bannerlord-release.ps1` (написан 16.08) сделан так же и кладёт в
архив ровно три файла: `SubModule.xml`, `bin/Win64_Shipping_Client/BannerlordLink.dll`
и `GUI/Prefabs/BLinkHeroNametag.xml`. Берёт их из git-дерева и вывода сборки, а
НЕ из папки игры — там рядом с модом лежат `config.json` с рабочим токеном,
копия исходников и восемь запасных DLL от прошлых откатов. Вторая линия защиты:
скрипт падает, если в списке появится путь с `config.json`, `.pdb`, `.backup`,
`.rollback`, `.crashy` или `/src/`. Обе защиты проверены подкладыванием ошибки
16.08 — отказ с названием файла, архив не создаётся.

**Оба упаковщика требуют PowerShell 7 и отказываются работать под 5.1**
(она пакует другими байтами, и архив перестаёт совпадать с манифестом).

**PowerShell 7.6.5 установлен 2026-08-16** (winget, вариант из Store). Ловушка:
он ставится псевдонимом в `WindowsApps`, а этой папки нет в PATH — поэтому
`pwsh` и `winget` по имени не находятся, хотя оба стоят. Звать полным путём:

```bash
"$LOCALAPPDATA/Microsoft/WindowsApps/pwsh.exe" -NoProfile -File scripts/pack-bannerlord-release.ps1 -OutputPath dist/releases/BannerlordLink-0.1.0.zip
```

Добавлять `WindowsApps` в PATH сознательно не стали: пользовательский PATH на
этой машине уже содержит полную копию системного, и лезть туда мимоходом
опаснее, чем писать полный путь.

Воспроизводимость проверена 16.08 на этом же pwsh: `pack-rimlink-release.ps1`
пересобрал канонический `RimLink-0.1.1.zip` **байт в байт** (`4e9656cb…ed42381`,
`cmp` без расхождений). То есть цепочка выпуска на этой машине снова рабочая, а
не «вроде должна собраться».

Проверка перед публикацией:

```bash
python -c "import zipfile,sys; n=[x for x in zipfile.ZipFile(sys.argv[1]).namelist() if x.endswith(('config.json','settings.xml'))]; print('SECRET FOUND:',n) if n else print('clean')" dist/releases/RimLink-0.1.1.zip
```

Вывод по-английски намеренно: консоль здесь ломает кириллицу. `clean` — архив
чист, `SECRET FOUND` — не публиковать. На `RimLink-0.1.1.zip` проверено 16.08,
ответ `clean`.

## 11. Локальная копия и поддельный мод

Полный стек на своём ПК: тот же бэкенд, тот же фронт, база — копия боевой из
вчерашнего бэкапа. Twitch о ней не знает, прод не участвует.

```bash
python scripts/local-setup.py      # развернуть; печатает команды запуска
```
Кладёт базу в `%USERPROFILE%\shedstream-local\` — **вне репозитория, намеренно.**
Локальная база рядом с кодом 2026-06-25 положила прод (её журнал уехал в архив
деплоя и затёр боевой). `deploy.ps1` теперь такие файлы исключает, но держать
базу снаружи — вторая линия защиты, независимая от той строки.

Путь к базе бэкенд берёт из `DB_PATH` (по умолчанию `viewers.db` — на
проде поведение не меняется). `FRONTEND_PATH` обязателен, иначе статика не
монтируется и копия открывается пустой (404 на `/static/*`).
Проверка: `curl http://127.0.0.1:8000/health` → `{"status":"ok","db":"ok"}`,
`/static/extension.html` → 200.

### Часы этого ПК опережают прод примерно на 20 секунд (2026-08-20)

Сверено `date -u` с обеих сторон. Поэтому одно и то же событие в логе мода и в
прод-базе отличается по времени на ~20 с, и это выглядит как «мод ответил
раньше, чем его спросили». Не паниковать: сверять по id действия, а не по
времени. Проверка одной командой:

```bash
ssh root@31.130.132.224 "date -u"; date -u
```

### Две ловушки локальной проверки — обе врут «зелёным» (2026-08-19)

**1. `FRONTEND_PATH` может указывать на брошенный git-worktree.** В
`%USERPROFILE%\shedstream-local\local.env` он был прописан на
`.claude/worktrees/hopeful-agnesi-ea9afe/…/frontend` (HEAD `03b1fa9`) — то есть
локальная проверка открывала фронт СТАРОГО коммита, а не рабочего дерева.
Симптом: свежий файл отдаёт 404, правки «не применяются», при этом всё
выглядит работающим. Путь исправлен на рабочее дерево 19.08.
**Проверять каждый раз, это одна команда:**

```bash
grep FRONTEND_PATH "$USERPROFILE/shedstream-local/local.env"
```

и в логе старта — строка `✅ Frontend папка подключена: <путь>`. Если там не
`…\Desktop\work\Расширение\frontend` — вы проверяете не тот код.

**2. Браузер кэширует JS по `?v=`, а во время ревью Twitch метка заморожена.**
Правишь `viewer.js`, перезагружаешь — браузер отдаёт СТАРЫЙ файл, потому что
`?v=` не менялся. 19.08 это едва не дало ложное «проверено в браузере»:
`window._bannerlordBuyAction` в странице был длиной 6108 символов, то есть
доработанный код вообще не грузился, а страница при этом работала.
**Как убедиться, что в браузере именно ваш код** — спросить у страницы:

```javascript
String(window._bannerlordBuyAction).length
```

**Как обновить локально, не трогая релизный cache-bust:** временно проставить
в обеих оболочках заведомо «будущую» метку, проверить, затем откатить
(`git checkout -- Расширение/frontend/extension.html Расширение/frontend/mobile.html`)
и убедиться, что `git status` по `frontend/` чист.
**Сначала закоммитить свои правки оболочек, потом бампать метку.** Откат
`git checkout` сносит ВСЁ незакоммиченное в этих файлах, а не только метку:
19.08 он вместе с меткой унёс свежий `<script src="viewer-registry.js">`, и
реестр перестал грузиться при внешне рабочей странице. Поймал это
`test_frontend_module_lifecycle.py` — проверкой «каждый `viewer*.js` с диска
подключён в обеих оболочках».

**Общий урок обеих ловушек:** «открыл локально и поработало» — не
доказательство, пока не подтверждено, ЧТО именно открылось. Проверять
идентичность запущенного кода, а не факт запуска.

**Чем это кончилось в тот раз:** только браузер и показал, что общий платный
путь бил в `undefined/api/shedcolony/action`. `const API_URL` и `let authToken`
в `viewer.js` объявлены на верхнем уровне классического `<script>` и **не
становятся свойствами `window`** — обращение через `window.API_URL` даёт
`undefined`. Node-тест этого не ловил, пока не стал гонять оба файла в одном
`vm`-контексте (`backend/tests/test_buy_action.js`). Правило: зависимости между
плоскими `<script>` брать ПО ИМЕНИ, а не через `window.*`.

### Поддельный мод — проверка модуля без запуска игры

`scripts/fake-mod.py` подключается по Module API как настоящий мод: здоровается,
шлёт события, забирает команды, подтверждает. Нужен потому, что у RimWorld нет
другого способа себя проверить — владелец в него не играет, и модуль полтора
месяца тихо расходился с реальностью.

```bash
python scripts/fake-mod.py --channel <id> --token <module-token>            # обычная работа
python scripts/fake-mod.py --channel <id> --token <t> --refuse-all          # проверка рефанда
python scripts/fake-mod.py --channel <id> --token <t> --drop-all            # зависшие команды
python scripts/fake-mod.py --channel <id> --token <t> --double-ack          # идемпотентность
python scripts/fake-mod.py --channel <id> --token <t> --send-event <тип>    # одно событие
```
Токен: из папки backend —
`python -c "import sys; sys.path.insert(0,'.'); from routes.streamer import issue_module_token; print(issue_module_token(98319857,'rimworld'))"`

Ловит класс «событие не объявлено в манифесте» мгновенно: отправка неизвестного
типа печатает `ОТВЕРГНУТО: event_not_in_manifest` и выходит с кодом 1. Этот
класс дважды жил в проде незамеченным.

**По не-локальному адресу не пойдёт** без явного `--i-know-this-is-prod`: он
пишет настоящие события в базу.

#### ⚠️ Для RimWorld почти всегда нужен `--rimworld-legacy`

**Без этого флага поддельный мод не увидит НИ ОДНОЙ платной покупки RimWorld —
и «проверка» не докажет ничего** (найдено 29.07, до этого в реестре стояло, что
трек C проверяется просто запуском fake-mod).

Причина: у RimWorld две очереди. `fake-mod` по умолчанию говорит по Module API
(`/v1/module/…`), а платные ручки RimWorld кладут команду в **старую** очередь —
таблицу `rimworld_pending_commands`, которую мод забирает через
`GET /api/rimworld/commands` и подтверждает через `POST /api/rimworld/ack-command`.
Адаптер RimWorld до сих пор объявляет `dispatch_action` заглушкой, поэтому
generic-очередь для него пуста всегда.

```bash
python scripts/fake-mod.py --channel <id> --token <t> --rimworld-legacy               # видеть покупки
python scripts/fake-mod.py --channel <id> --token <t> --rimworld-legacy --refuse-all  # проверка возврата
```

#### Готовые прогоны аудита работы (прод не трогают)

```bash
python scripts/audit-rimworld-track-c.py   # трек C: 6 механик RimWorld, exit 0 = всё сошлось
python scripts/audit-guild-skill.py        # прокачка навыка гильдии, 29 проверок
```

Первый требует поднятого локального бэкенда и строки
`TESTING_BYPASS_STREAM_LIVE=true` в `local.env` — иначе платные ручки RimWorld
блокирует проверка «идёт ли стрим», и прогон упрётся в неё, а не в механику.
Он сам достраивает то, чего в проде нет: присылает каталог магазина как мод
и заводит пешку — без этого половина механик отвечает «пешка не найдена».

**Три ловушки этих прогонов** (все стоили ложных красных, записаны чтобы не
расследовать заново):

- **Первая покупка в RimWorld выдаёт достижение и НАЧИСЛЯЕТ 500💎** — на балансе
  это выглядит как «списали меньше цены».
- **Кулдаун лечения лежит в базе** и переживает прогон: второй запуск подряд
  видит «ещё 13 минут» и считает это провалом лечения.
- **`Database` заводит собственный пул**, и глобальный `close_db_pool()` его не
  закрывает — прогон висит до таймаута при полностью зелёной печати. Судить по
  коду возврата, а не по тексту (`CLAUDE.md`, «Судить о тесте по КОДУ
  ВОЗВРАТА»).

## 13. Вопросы владельца и регулярная уборка

### Три вопроса, которые не устареют

Они про суждение, а не про процесс, поэтому их нельзя автоматизировать —
и задавать их можно годами.

**1. «Что это будет стоить, если ты ошибся?»**
Определяет, сколько проверять ПЕРЕД действием. Локальная правка — ошибайся
свободно, переписывается. Прод, Steam Workshop, публичный релиз, миграция
данных — сначала думай. Самый дорогой класс ошибок проекта живёт именно тут:
казино построено и вырезано, механики по мотивам BLT и последующий аудит
лицензии, фронт, замёрзший на чужом CDN.

**2. «Чем докажешь?»**
Не «ты уверен» (на это я отвечу «да»), а «покажи». На втором либо показываю,
либо обнаруживаю, что показать нечем. Отсюда растут «видел красным?» и
«не протухло ли?».

**3. «Кому от этого станет лучше?»**
Живому зрителю на живом стриме — или только нам внутри? Второе иногда
необходимо, но если перевешивает, мы строим инфраструктуру вместо продукта.
Слово «платформа» очень удобно это оправдывает.

### Семь частных случаев — строительные леса

Каждый выведен из реального промаха и **должен со временем исчезнуть**: вопрос,
который приходится задавать месяцами, — признак несделанной автоматизации, а не
постоянный инструмент.

| Вопрос | Когда | Из какого промаха | Куда девается |
|---|---|---|---|
| «Что из этого уже есть?» | до того как я пишу новый инструмент | 2026-07-26: написал второй поддельный мод, не заметив первый в `tests/` | должно стать моей привычкой |
| «Это обратимо?» | всё, что уходит наружу | казино, BLT, замёрзший фронт | частный случай вопроса №1, останется |
| «Ты видел это красным?» | я отчитываюсь, что работает | 2026-07-26: едва не отрапортовал нерабочий фикс — смотрел на код конвейера, а он возвращал успех фильтра | **правило 2b в CLAUDE.md** |
| «Не протухло ли то, на что ссылаешься?» | я пересказываю статус из документа | 2026-07-25: три устаревших факта за день (офсайт, размер `viewer.js`, мониторинг) | **правило 8b в CLAUDE.md** |
| «Что из этого почувствует зритель?» | список дел похож на инфраструктуру | сползание в «платформу» | частный случай вопроса №3, останется |

**Если вопрос три раза подряд дал ответ «всё чисто» — убрать его.** Список
вопросов гниёт ровно так же, как набор тестов.

### Регулярная уборка — это ритуал, а не вопрос

У неё другой ритм: по календарю, а не по поводу. Раз в месяц-полтора.

**«Проведи проверку актуальности тестов».** Прохожу по всему набору и отвечаю по
каждому: что ловит · во что обошлась бы эта поломка · не проверяет ли он ФОРМУ
кода вместо поведения (такие мешают переделкам — худший вид) · ни разу не
краснел и стал структурно невозможен · не дешевле ли перенести в линтер.
Предлагаю удаления списком. Набор гниёт молча: медленный перестают гонять, а
потом пропускают и настоящую поломку.

**Независимый аудит сторонней моделью.** Раз в пару месяцев или перед
подачей на ревью. Бриф — `docs/EXTERNAL_AUDIT_BRIEF.md`, копируется целиком.
Смысл не в «второй модели», а в читателе, который НЕ писал этот код: свои
допущения изнутри не видны. Просить строго три класса — деньги, изоляция
каналов, авторизация; всё остальное даёт шум. Требовать по каждой находке
сценарий отказа и способ доказательства. **Основной помощник проверяет находки
на свой же код и заинтересован их отклонить — отклонение без доказательства не
принимается.**

*Почему это работает — механизм, а не «свежий взгляд» (зафиксировано 2026-07-28
после трёх прогонов).* Слепые пятна порождаются самим авторством:
- **код читается как задуманный, а не как написанный.** Про кассу было известно,
  что она списывает атомарно, — проверялось ровно это. Что путь ПОСЛЕ неё теряет
  цену, в голову не приходило: в модели автора цена уже учтена (PB-01, три
  месяца, 74 случая невозвращённых денег);
- **смотрят туда, где чинили.** Все внутренние прогоны шли по свежим правкам;
  старый «стабильный» код не перечитывает никто;
- **проверки наследуют допущения автора.** Тест кассы писал тот же, кто писал
  кассу, и он покрывает обычную ветку — потому что автор думал о кассе как об
  одной ветке. Такой тест структурно не может поймать непредставленное.

*Как использовать правильно, по результатам прогонов:*
- **давать ДАННЫЕ, а не только код.** Аудит по копии боевой базы дал 3 из 3 —
  лучший результат; аудит по одним исходникам давал 12 из 15 и один ложный
  блокер. Данные не разделяют авторских допущений вообще;
- **не перечислять заранее, что уже проверено** — иначе внешний наследует ту же
  рамку и перестаёт быть внешним;
- **в бриф класть, какие URL обслуживает бэкенд, а какие лежат в архиве.**
  Единственный ложный блокер (privacy/terms «отдают 404») родился именно из
  того, что в пакете этого не написали;
- просить сценарий отказа и способ проверки, а не мнение о качестве.

**«Что мы можем удалить?»** Мёртвый код, неиспользуемые механики, устаревшие
документы, дубли инструментов, мусор в рабочей папке — списком, с оценкой, что
сломается. Площадь поддержки растёт сама и сокращается только руками; без этого
ритуала правило «фича входит — фича выходит» не работает.

## 14. Стрим-железо: микрофон и звук в OBS

### QuadCast S теряет «паспорт»: `USB Advanced Audio Device`

**Симптом.** Микрофон в Windows называется `USB Advanced Audio Device` вместо
`HyperX QuadCast S`, в звуке помехи и провалы.

**Что это.** Внутри QuadCast S два устройства за общим USB-хабом: контроллер
(кнопка, RGB) и аудиокодек C-Media. У кодека слетает EEPROM — микросхема с
дескрипторами — и он поднимается на заводских значениях C-Media. Известная
болезнь модели, не уникальная поломка. Помехи — часть той же причины: в EEPROM
лежат и настройки аудиотракта.

**Как отличить от всего остального — по VID/PID, а не по имени:**

```powershell
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match 'VID_0D8C|VID_0951&PID_171' -and $_.Class -in @('MEDIA','USB') } | ForEach-Object { $_.InstanceId }
```

| аудиочасть | значит |
|---|---|
| `VID_0951&PID_171D` | здорова |
| `VID_0D8C&PID_016C` | EEPROM слетел |

Контроллер `VID_0951&PID_171F` остаётся жив в обоих случаях — по нему судить
нельзя, и NGENUITY видит микрофон именно через него. **«NGENUITY видит устройство»
не означает, что оно исправно.**

**Случай 2026-08-26:** слетело при холодной загрузке в 22:00. Гарантия истекла.
Официальные файлы прошивки лежат локально в пакете NGENUITY из Microsoft Store,
названы по VID+PID: `Assets/Firmware/0951171D.bin` (256 Б — размер EEPROM) и
`0951171F.bin`. Сторонний прошивальщик с файлообменника ходит по форумам —
**на этой машине не запускать никогда:** здесь SSH-ключи к проду, `.env` с
токенами Twitch и боевая база; цена ошибки не микрофон, а канал и сервер.
Прошивать только с чужой машины либо через поддержку HyperX.

### Ложные следы, на которые ушло время

- **Ошибки сети в логе NGENUITY** (`HttpRequestException`) — это Google Analytics,
  её режет AdGuard. К прошивке отношения не имеют, VPN не нужен. Смотреть надо
  стек: `GoogleMeasurementProtocol` в нём и стоит.
- **Хаб `VID_1A40&PID_0801` рядом с микрофоном — не внешний, он внутри самого
  QuadCast.** Признак: на нём висят только две части микрофона и больше ничего.
  Перетыкание портов лечит не это.
- **Обновление NGENUITY ≠ прошивка микрофона.** Проверять по журналу
  `Microsoft-Windows-Kernel-PnP/Configuration`: при реальной прошивке устройство
  ресетится и перечисляется заново. Нет событий USB — прошивки не было.

### Микрофон в OBS держать на «По умолчанию»

Аудиочасть перечисляется **без серийного номера**, поэтому Windows выдаёт ей
новый endpoint GUID при каждом перетыкании, а в журнале пишет «параметры не
перенесены из-за неоднозначного совпадения устройства». Источник в OBS,
привязанный к конкретному GUID, после этого молча пишет тишину — в логе OBS
видно как `Failed to activate client context: 88890004`.

Проверка перед эфиром — сверить device_id активной сцены с живыми endpoint'ами:

```powershell
$j=Get-Content "$env:APPDATA\obs-studio\basic\scenes\*.json" -Raw -Encoding UTF8 | ConvertFrom-Json
$j.PSObject.Properties | Where-Object Name -match 'AudioDevice' | ForEach-Object { $_.Name + ' -> ' + $_.Value.settings.device_id }
Get-PnpDevice -Class AudioEndpoint -Status OK | Where-Object InstanceId -match '0\.0\.1' | Select-Object FriendlyName,InstanceId
```

Отвалы микрофона под нагрузкой считаются по логам OBS:

```bash
grep -c invalidated "$APPDATA/obs-studio/logs/<последний>.txt"
```

До 20.08 во всех логах ноль; 28.08 — три отвала и два отказа запуска за три
минуты. Это и есть объективная мера «помех», а не ощущение на слух.
