## Шаг 1 — Твоя часть подачи (Twitch Dev Console)

1. **Скриншот** живого расширения **1024×768** (соотношение 4:3) — открой панель на своём канале,
   сделай скрин. (Логотип 100×100 и discovery 300×200 уже готовы: `Расширение/docs/submission-assets/`.)

2. **Dev Console → твоё расширение → Version 1.0:**
   - **Files**: загрузить фронт-`.zip` (папка `frontend/`) → дождаться, пока встанет в **Hosted Test**.
   - **Asset Hosting**: убедиться, что Panel/Video-Overlay/Mobile/Config указывают на нужные html
     (`extension.html` / `overlay.html` / `mobile.html` / `config.html`).

3. **Заполнить форму версии** (поля и точные значения):

   | Поле | Значение |
   |---|---|
   | Summary / Description | из `REVIEW_SUBMISSION.md` §1 (что такое ShedLink) |
   | Category | Game Integration / Engagement |
   | Privacy Policy URL | `https://shedoy23.ru/privacy.html` |
   | Terms of Service URL | `https://shedoy23.ru/terms.html` |
   | Screenshots/Icons | скриншот 1024×768 + logo 100×100 + discovery 300×200 |
   | **URL Fetching Domains** (CSP allowlist) | `shedoy23.ru` |
   | Bits support | **No** |
   | Subscription support | **No** |
   | Reviewer notes | вставить весь текст `REVIEW_SUBMISSION.md` |

4. **Тестовый канал должен быть LIVE** в окно ревью (твой канал `twitch.tv/shedoy23`), с запущенной
   игрой нужного модуля — ревьюер тестирует на живом стриме.

5. **Submit for Review.**

## Шаг 2 — Что после Submit (без паники)

- **Аудитория НИЧЕГО не видит**, пока ты сам не нажмёшь **Released**. Подать ≠ опубликовать.
- Цикл: Local Test → Hosted Test → **In Review** → Approved → (ты жмёшь) **Released**.
- Сроки ревью: **~2–11 рабочих дней**.
- Если попросят поправить — это **Pending Action** (письмо на email, НЕ отказ): чинишь → переподаёшь.
  Resubmit сбрасывает место в очереди → дешевле подать чисто один раз.
- Необратим только **Rejected** (отзывают Client ID навсегда) — но это для откровенных нарушений;
  compliance у нас чистый, такого исхода не ждём.

## Как работать дальше, пока проверяют v1.0

Главная мысль: **замораживается не ты, а один снимок фронта.**

**1. Фронт под ревью — это .zip-снимок.** Для новой работы заводишь **новую версию** (1.0.1 / 1.1) в
   Dev Console — она отдельная, ревью её не касается. Старую версию не трогаешь, пока проверяют.

**2. Бэкенд — ОДИН на всех** (`shedoy23.ru` обслуживает и версию под ревью, и твою разработку).
   Это главное место, где надо быть аккуратным во время ревью:

   | Действие на проде во время ревью | Можно? |
   |---|---|
   | Добавить **новое** (ручка/поле/механика, которых submitted-фронт не знает) | ✅ Да — он их не вызывает |
   | Изменить/переименовать/удалить то, что submitted-фронт **уже дёргает** | ❌ Нет — у ревьюера упадёт → отказ |
   | Крупная/рискованная переделка (контракт API, переписать покупки) | ⚠️ Не на прод — через staging |

**3. Staging — твой полигон.** `pwsh scripts/deploy.ps1 -Staging` поднимает отдельный инстанс на
   **:8001** (своя БД, своя `.env`, `DISABLE_LIVE_INTEGRATIONS=1` — не лезет в живой чат/EventSub,
   autostart выключен). Рискованное гоняешь там, прод не трогаешь. Выключить после теста:
   `ssh root@31.130.132.224 'supervisorctl stop twitchbot-staging'`.

**4. Стримить можно как обычно** — прод живой, фичи работают.

**5. RimWorld-кластер (5 отложенных багов)** — это бэк-правки для выключенного модуля. Когда вернёшь
   RimWorld, гоним их **через staging** (там проверим в игре), не вслепую на прод. Напоминание-чип уже висит.
