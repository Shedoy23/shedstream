## 0. Диагноз: что изначально построено неверно

Корневой паттерн один: **«сначала строю — ограничения проверяю потом»**.
Он уже оплачен четыре раза:

| # | Ошибка | Доказательство | Цена |
|---|---|---|---|
| 1 | Казино построено → правила Twitch проверены потом | вырезано целиком (Phase 1 compliance) | недели работы в корзину |
| 2 | Модель скопирована с BLT → лицензия (LGPL) «потом» | clean-room аудит до сих пор **блокер публичного релиза** | проект не может выйти на Twitch, пока не закрыт |
| 3 | «Работает у меня» → секьюрити потом | аудит 2026-04-30: **13 CRITICAL**; JWT доделывался в июне | повезло, что нашли сами |
| 4 | Один канал → мультитенант потом | `m1_multitenant.py` — ретрофит всей схемы | большая миграция + хвост channel_id-багов |

Структурные следствия «наития» (не фатально, но тормозит каждый день):

- **Тестов де-факто нет** — проверка = «задеплоить в прод посреди стрима и
  смотреть логи». Каждый баг находят зрители. Падающий тест (exit 2) никого
  не останавливал — сигнал мёртв.
- **viewer.js ~7k строк** — один файл, две игры, без сборки. Каждая правка —
  риск регресса в соседней игре (FLICKER-FIX дошёл до «v7»).
- **Площадь фич растёт бесконтрольно** — питомцы, дуэли, кубики, TTT, TTS,
  кейсы, гильдии… Каждая фича — вечная аренда (её надо чинить при каждом
  изменении), а данных «что реально юзают» нет.
- **Прод = дев** — один VDS, деплой во время стрима, offsite-бэкапа нет,
  игровой ПК = стримерский ПК, версия движка прибита руками (инцидент 1.4.5).

Что построено **правильно** (не трогать, поддерживать): Module API и
мультитенантное ядро, outbox+рефанды, data-driven баланс (ребаланс миграцией
без пересборки мода), защитные Harmony-финализаторы, deploy.ps1 + pre-commit
lint, CONTEXT-доки, привычка «прогнать агентов по логам после стрима».

## 1. P0 — обязательно в ближайшие ДНИ

### [x] 1.1 Offsite-бэкап БД ✅ 2026-06-11
Самый дешёвый катастрофический риск: умер VDS — умерло всё (поинты зрителей,
герои, экономика).
**Сделано:**
- ПК ежедневно тянет последний `.zst`-снапшот с прода (`scripts/pull-backup.ps1`),
  хранит 14 копий в `%USERPROFILE%\shedstream-backups\`. Планировщик Windows
  `shedstream-db-backup-pull` (daily 13:00 + StartWhenAvailable). Проверено
  end-to-end (LastResult 0x0).
- **Бонус-находка:** прод-cron бэкапа был **мёртв 10 дней** (деплой ~1 июня
  снёс флаг +x → `Permission denied`). Починено: `chmod +x` + cron переведён
  на `/bin/bash …` (иммунно к потере +x). In-process `backup_loop.py` всё это
  время прикрывал, так что данные не были голыми.
- **Остаётся (→ 2.2):** реальный restore-drill — развернуть бэкап и убедиться,
  что он рабочий.

## 3. Постоянные правила (вставить в CLAUDE.md и требовать исполнения)

Это главный рычаг: ты управляешь проектом через промпты и CLAUDE.md.
Наитие генерирует «что строить», но не видит «что проверить ДО» и «что
чинить ПОСЛЕ» — эти две вещи должны быть правилами.

1. **Новая механика = сначала проверка, потом код.** Перед любой новой фичей:
   (а) compliance-чек по правилам Twitch, (б) лицензионный чек если идея из
   BLT, (в) короткая спека на согласование. Код — только после «ок».
2. **«Готово» = доказательство.** Не «сделал», а вывод тестов / строка лога /
   скрин. Красный тест = стоп.
3. **На прод — после стрима.** Во время стрима только hotfix падающего прода.
4. **Фича входит — фича выходит.** Перед добавлением новой механики назвать
   одну старую из анти-топа метрик, которую замораживаем/убираем.
5. **Раз в месяц — аудит-сессия вместо фич** (секьюрити / дохлый код /
   техдолг / зависимости). Апрельский аудит окупился лучше любой фичи.
6. **Каждое значимое изменение — в CONTEXT-док.** (Уже делается — не бросать.)

## 4. Чего НЕ делать сейчас

- **Не добавлять новые крупные механики**, пока не закрыты 1.4 (BLT) и 1.5
  (compliance) — каждая новая фича увеличивает объём аудита и риск переделки.
- **Не переезжать с SQLite / не переписывать на «правильный» стек.** Для
  текущего масштаба всё работает; переписывание — самый дорогой способ
  ничего не улучшить. Вернуться к вопросу, когда появится второй-третий
  реальный канал.
- **Не полировать то, что не болит** (рефакторинг ради красоты). Болит:
  тесты, compliance, бэкапы, viewer.js.

- [ ] Offsite-бэкап работает + восстановление из него один раз реально прогнано.
- [ ] Из 13 CRITICAL аудита закрыто всё (включая RimWorld mod-ingest).
- [ ] Прод мониторится; о падении узнаёшь от бота, а не от зрителей.
- [ ] По каждой фиче есть цифры использования; анти-топ заморожен.
- [ ] viewer.js распилен; правка Bannerlord-кода не трогает RimWorld.
- [ ] Правила из раздела 3 живут в CLAUDE.md и реально применяются.

После этого — следующий горизонт: Twitch submission, второй реальный

## 6. Структура работы (чтобы недели не уходили в пустоту)

### Четыре типа сессий — называй тип в начале

Главный источник «пустоты» — сессии без рамки: начали с фичи, свернули в баг,
закончили рефакторингом, ничего не доведено. Лечится одним словом в начале:

| Тип | Когда | Стартовый промпт |
|---|---|---|
| **Фикс-сессия** | после каждого стрима, 15–30 мин | «Запусти агентов по вчерашним логам, разбери, почини найденное» |
| **Долг-сессия** | 1–2 вечера в неделю | «Берём следующий пункт из ROADMAP P0/P1: …» |
| **Фича-сессия** | только когда P0 пуст | «Хочу механику X. Сначала compliance/лицензия/спека, код после моего ок» |
| **Аудит-сессия** | раз в месяц | «Месяц прошёл — аудит: секьюрити / дохлый код / техдолг» |

Правило: **одна сессия = один тип = один результат.** Если посреди фичи
нашёлся баг — записать в список, не переключаться (кроме горящего прода).

### Ритм недели (ориентир)

- **После стрима:** фикс-сессия по логам (то, что мы уже делаем — это работает).
- **1–2 вечера:** долг-сессии по этому файлу, сверху вниз. Не выбирать
  «что интереснее» — выбирать следующий незакрытый чекбокс.
- **Фичи:** в очередь (ниже), реализация — когда P0 закрыт.
- **Раз в неделю, 5 минут:** открыть этот файл, отметить сделанное, посмотреть
  что следующее. Файл живой — устарел пункт, попроси Клода обновить.

### Как формулировать задачи (анти-пустота)

1. **Цель, а не решение.** «Зрители не понимают, почему действие не сработало»
   лучше, чем «добавь тост». Решение Клод предложит сам — и часто дешевле.
2. **Одна задача — одна сессия.** «Сделай X, и ещё Y, и заодно Z» = три
   полусделанных вещи. Большое — попроси разбить: «разбей на шаги, делаем по одному».
3. **Для крупного — сначала план.** «Покажи план/спеку, код после моего ок».
   Отменить план — бесплатно; отменить написанное — больно (казино).
4. **В конце сессии — сводка.** «Что изменилось, что где задеплоено, что мне
   сделать руками». (Теперь это правило #7 в CLAUDE.md — Клод обязан сам.)
5. **Идеи — в очередь, не в работу.** Пришла идея механики → одной строкой в
   список идей (или сюда), а не «давай сделаем сейчас». Раз в неделю-две —
   разобрать очередь и выбрать одну по данным использования.

### Чем «уверенный уровень» отличается от текущего — в одну строку

Сейчас: *что-то сломалось → узнаём от зрителей → чиним на живую.*
Цель: *ломается на staging → тесты краснеют → зрители ничего не заметили.*
Каждый пункт P0/P1 — шаг этого перехода.
