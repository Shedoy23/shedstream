# Twitch Stream Platform — Vision & Starter Guide

Документ для быстрого входа в контекст в новом чате.

## Видение продукта

**Twitch-расширение-платформа с виртуальной экономикой и подключаемыми модулями интеграции с играми.**

- **Ядро (always on, game-agnostic):** очки за просмотр, инвентарь, казино, дуэли, рынок, семьи, ивенты, квесты, чат-награды, кастомизация. Работает у любого стримера независимо от того что играет.
- **Модули интеграции (опциональные, включаются стримером):** двусторонняя связь с конкретной игрой. Стример выбирает в админке: «играю в RimWorld» → активен RimWorld-модуль; завтра «играю в Minecraft» → переключился на Minecraft-модуль.
- **Уникальное позиционирование на рынке:** StreamElements/StreamLabs дают лоялти-очки и оверлеи, но НЕ делают глубокую двустороннюю интеграцию с играми. Crowd Control делает интеграцию, но без своей экономики и миниигр. Этот продукт = их пересечение, ниша никем не закрыта.

### Module API (концепт, требует детального дизайна перед кодом)

Каждый модуль реализует стандартный интерфейс:

**События ИЗ игры → ядро:**
- `player_joined`, `player_left`
- `item_gained(item_type, quantity)`
- `level_up(new_level)`
- `death`, `quest_completed`
- кастомные события модуля

**Действия ИЗ ядра → игра:**
- `spawn_item(item_id, quantity, target_player)`
- `apply_buff(buff_id, duration, target_player)`
- `trigger_event(event_id, params)`
- `give_currency(amount, target_player)`

**Custom UI слоты:** модуль может добавлять свои фронт-панели/кнопки.

**Транспорт:** WebSocket с авторизацией по channel_id (сейчас REST → переходим).

**Версионирование API:** старые модули продолжают работать после обновлений ядра.

## Первые шаги (что делать прямо в следующем чате)

**Шаг 1 — Module API спецификация (1 неделя, до кода):**
- Перечислить все события которые отдаёт RimWorld-модуль сейчас → найти общие для других игр (Minecraft, Terraria) → выделить «универсальные» в core API, остальные в `extensions`
- То же для actions
- Описать формат manifest'а модуля (id, version, supported_core_version, events, actions, ui_slots)
- Зафиксировать в `Расширение/docs/MODULE_API.md`

**Шаг 2 — параллельно: валидация рынка** (не блокирует код, делается своими руками):
- Написать 5-10 RU Minecraft/RimWorld-стримерам в личку: «делаю расширение с экономикой + интеграцией в твою игру, готов отдать тебе бесплатно за фидбек когда будет готово»
- Откликнулись 2-3 → рынок есть, идём кодить
- Откликнулись 0-1 → пересмотреть позиционирование или нишу

**Шаг 3 — Multi-tenant рефакторинг:**
- В каждом запросе извлекать `channel_id` из JWT
- Все ключевые таблицы дополняются `channel_id` либо разделяются на отдельные SQLite-файлы (один на стримера)
- Все эндпоинты ВАЛИДИРУЮТ что действие совершается над данными совпадающего channel_id
- Тестовый сценарий: два стримера, действия одного НЕ ВИДНЫ другому

**Шаг 4 — вынос RimWorld в модуль:**
- Создать структуру `Расширение/backend/modules/rimworld/`
- Перенести `routes/` касающиеся RimWorld + сервисы
- Ядро дёргает модуль через стандартный интерфейс, не знает про специфику RimWorld

## Главные риски и как их снимать

1. **Module API дизайн** — самое критичное решение. Облажаешься = переделывать всё. Снятие: 1-2 недели на бумажную спецификацию ДО кода
2. **Это марафон, не спринт** — год до устойчивого MRR. Снятие: closed beta даёт ранние сигналы валидности через 3-4 месяца
3. **Поддержка одиночке** — N клиентов = N тикетов. Снятие: документация + Discord-комьюнити + SDK для community-модулей
4. **Bus factor** — ты один. Снятие: код пишется чисто, с прицелом «передать команде через год»
5. **Twitch может изменить политики** — маловероятно но возможно. Снятие: смотри Twitch Developer changelog ежемесячно

## Что НЕ делаем

- ❌ Прямую покупку очков за деньги внутри расширения (нарушает Twitch TOS)
- ❌ Bits-монетизацию (отсёк сам — RU-аудитория не пользуется)
- ❌ Параллельно: Steam-арбитраж, ставки, читы, gold-фарм. Если этот проект пошёл — фокус только на нём
- ❌ Сразу строить идеально — первые 3-6 месяцев это поиск product-market fit, рефакторинг будет
