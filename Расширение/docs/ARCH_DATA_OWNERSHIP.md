# ARCH-1 — Честный разбор: «кто владеет данными» (SQL vs game save)

> Дата: 2026-05-29. Разбор совета друга про SQL data ownership.
>
> ⚠️ Я анализирую тезис как «у тебя дублируется игровое состояние в SQL —
> заведи один источник истины». Если друг имел в виду другое — поправь, и я
> переориентирую разбор.

---

## 1. Что на самом деле происходит (факты из кода)

У нас **два хранилища**, и они частично пересекаются:

| Хранилище | Что держит | Авторитетность |
|---|---|---|
| **Backend SQLite** (`viewers.db`) | ⦷-баланс (crustic), `bannerlord_heroes`, `_vassals`, `_workshops`, `_fiefs`, `_caravans`, `_heirs`, `inheritance_log`, очередь `module_actions` | разное (см. ниже) |
| **Bannerlord save** (мод SyncData + engine) | `Hero`/`Clan`-объекты, золото (динары), кто жив, `_vassalToMaster`, `_vassalLastGold` | авторитет по игровому состоянию |

Связь — **не прямая**: расширение (Twitch iframe) говорит только с backend по
REST; мод говорит только с backend. Между собой мод и фронт **не общаются**.
Синхронизация идёт через:
- **Outbox** — backend кладёт `module_actions`, мод поллит и применяет.
- **События** — мод шлёт назад (`hero.vassal_created` с реальным clan_id,
  profit-sync мастерских, tribute-sync владений) → backend обновляет строки.
- **Backfill-танец** — backend вставляет `placeholder_clan_id`, мод создаёт клан,
  возвращает реальный id, backend апдейтит. Это **прямое доказательство**
  раздвоенного владения одним фактом.

## 2. Где друг ПРАВ

Там, где **один и тот же факт авторитетно пишется в обоих местах** — это
классический split-brain, и он уже стоит нам кода:

- `vassal_clan_id` — backend выдумывает placeholder, мод выдаёт настоящий →
  целый backfill-флоу ради рассинхрона, который мы сами и создали.
- profit мастерских / tribute владений — реальные числа живут в игре, копии
  в SQL, плюс `ProfitSyncBehavior` / `FiefTributeSyncBehavior` существуют
  **только чтобы гонять числа туда-обратно**.
- `income_share_pct` — лежал в SQL и до сегодня **никем не применялся** (мод
  про него не знал). Классика: данные есть, владелец-исполнитель — нет.

Вывод друга в этой части верный: **дублирование игрового состояния в SQL →
вечная борьба за консистентность**.

## 3. Где «один источник истины» НЕ применим (нюанс)

Наивное «снести SQL, пусть всё живёт в сейве» — сломает продукт:

1. **Фронт не видит игру.** Twitch-расширение физически не может читать save.
   Ему нужна REST-проекция. Что-то backend хранить **обязан**.
2. **Игра бывает оффлайн.** Стрим не идёт, а зритель листает расширение,
   тратит ⦷, ставит в очередь действия. Save в этот момент недоступен.
3. **Мультитенант.** Один backend на много каналов; save — на машине стримера.
4. **⦷-экономика — НЕ игровое состояние.** Crustic/Bits/Boosty — это
   Twitch-экономика, её владелец backend по определению, в сейве ей не место.

То есть «единый источник истины» как абсолют — неверно для этого продукта.

## 4. Правильная формулировка (моя позиция)

Не «один владелец на всё», а **чёткое владение per класс данных** + явный
статус «авторитет vs проекция»:

| Класс данных | Владелец (authority) | Второе хранилище = |
|---|---|---|
| ⦷-баланс, очередь действий, viewer↔hero binding, конфиг (`income_share_pct`, цены) | **Backend** | — (мод только читает) |
| Игровое состояние: `Hero.Gold` (динары), `Clan`, кто жив, реальные clan_id | **Мод/save** | backend-строка = **кэш/проекция** (eventually-consistent) |

Правило: для игровых сущностей backend-строка — **read-model/проекция**, а не
второй авторитет. Тогда:
- backfill `placeholder→real` остаётся (это нормальный outbox-pattern), но мы
  **перестаём притворяться**, что SQL-копия профита/tribute авторитетна —
  она просто отображается фронту, мод её перезатирает.
- sync-behaviors остаются как **проекторы** (game→backend), но **никогда**
  наоборот для этих полей.

Друг прав на 70%: проблема реальна, но решение — не «убить SQL», а
**пометить каждое поле: authority или projection** и запретить двунаправленную
авторитетную запись.

## 5. Конкретные действия (если решим чистить)

1. **Документировать владение** — таблица §4 в `ARCHITECTURE.md` как инвариант.
2. **Пометить projection-поля** — `*_workshops.total_profit`, `_fiefs.total_collected_dinars`,
   `_vassals.vassal_clan_id` → коммент «MOD-AUTHORITATIVE, projection only».
   Backend никогда не пишет их по своей инициативе, только из game-события.
3. **Конфиг ≠ состояние** — `income_share_pct` явно backend-config (ок), мод
   читает через payload (сейчас захардкожено 25% — можно прокинуть из строки).
4. **Не расширять дублирование** — новые фичи: решать заранее authority/projection,
   не плодить «backend выдумал id → мод поправил».

## 6. Вердикт

- **Совет полезный и по делу** — split-brain у нас реально есть и уже стоил кода.
- **Но абсолют «единый источник» неприменим** — фронт/оффлайн/мультитенант/
  ⦷-экономика требуют backend-хранилища.
- **Минимальный практичный шаг** (низкий риск, без переписывания): зафиксировать
  владение per-поле и запретить двунаправленную авторитетную запись. Это
  убирает причину будущих рассинхронов, не ломая текущее.
- **Не делать сейчас** большой рефактор «снести/слить хранилища» — высокий риск,
  низкий немедленный профит; продукт работает.
