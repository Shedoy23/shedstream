# Изолированный React-пилот турнира

Локальный кандидат. Это отдельный, намеренно ограниченный макет: он не загружает
legacy viewer.js, не монтируется в выпущенную панель и не меняет её DOM.
`index.html` всегда использует синтетический `PreviewTransport`: переключателя
на production нет, HTTP-транспорт не попадает в итоговый JS. Никаких списаний,
запросов к EBS, push, деплоя или замены замороженного Twitch ZIP.

## Воспроизведение

Нужен Node.js 22.12+ (проверено Node 24.19.0, npm 11.9.0).
Из корня репозитория:

```sh
npm --prefix frontend-next ci
npm --prefix frontend-next test
npm --prefix frontend-next run typecheck
npm --prefix frontend-next run build
npm --prefix frontend-next run preview
```

Открыть `http://127.0.0.1:4173`. В этом окружении при недоступном системном npm
cache можно добавить `--cache /tmp/shedlink-pilot-npm-cache` к npm ci.
Проверять именно статическую сборку через preview: строгий CSP здесь не
предназначен для Vite HMR. `dist/` одноразовый, игнорируется Git; корневой
`dist/` и упаковщик существующего расширения не используются.

Переключатель показывает очередь, пустую очередь, действующий турнир,
подтверждённую запись, прогноз, отказ сервера, ошибку загрузки и неизвестный
исход заявки. Все имена и данные вымышленные. Отказ/неизвестный исход заявки
появляются после нажатия «Вступить». Reload сбрасывает весь локальный пример.

## Границы ответственности

- `contracts.ts`: текущие DTO и только два существующих действия
- `transport.ts`: GET/POST, текущий JWT при каждом вызове, UUID, single-flight,
  сохранение текстов отказа и метаданных, неизвестный исход без повторного POST
- `auth.ts`: один host-owned подписчик Twitch onAuthorized, токен только в памяти
- `controller.ts`: один владелец состояния, отмена GET, подавление старых ответов,
  сброс при смене зрителя/канала, серверный кулдаун и подтверждение действием снимка
- `TournamentView.tsx`: React выводит текст, открывает/закрывает подтверждение;
  серверные строки никогда не становятся HTML
- `main.tsx` + `preview.ts`: только автономный демонстрационный вход

Здесь нет второй реализации общего платного dispatch-пути: адаптер разрешает
только `hero.join_tournament` с `{price:0}` и бесплатный
`tournament.predict` с `{target}`. Обёртка POST соответствует существующему
`{action_type,data:{...,client_action_id}}`. Цена из GET, отличная от нуля,
не открывает платный вход. Баланс/платные действия в этом пилоте отсутствуют.

Принятие POST не означает применение в игре. Для записи нужен последующий
GET.in_queue или участие этого зрителя в начавшемся турнире. Для прогноза
используется GET.my_prediction текущего раунда. Пока подтверждение записи не
пришло, новая мутация заблокирована, безопасное обновление доступно. Новая
турнирная сессия/раунд закрывают старое окно подтверждения.

При сетевой ошибке или непонятном результате POST HTTP-адаптер не повторяет
запрос и удерживает блокировку для этой пары канал/зритель до конца своей жизни.
Смена токена её не снимает. POST не отменяется при unmount, потому что отмена
HTTP не отменяет действие сервера; поздний результат не перерисовывает старый
экран. Если тот же controller запускается снова, он сначала сверяет зрителя и
канал: чужие данные/исходы очищаются до первого GET. Ответ своего POST,
полученный во время остановки, сохраняется без перерисовки и применяется при
повторном запуске. Явный отказ снимает ожидание; успех ждёт подтверждения
снимком; неизвестный исход остаётся заблокированным. Два дефекта этого пути
нашёл независимый обзор: старый зритель сохранялся при restart и ответ POST
терялся из-за общей lifecycle-защиты. Шесть регрессионных сценариев увидели
красными до исправления (57075a2), затем прошли.
Это консервативный предел пилота, не durable exactly-once гарантия после
перезагрузки вкладки. У backend-only прогноза нет module_actions-строки для
обычного UUID replay, поэтому автоматические и ручные retry здесь отсутствуют.

## Что ещё не доказано и не входит в паритет

- Подключение к живому EBS, Twitch Local/Hosted Test и reviewer submission
- Встраивание в desktop/mobile legacy оболочки. Перед ним требуется явная
  передача единственного владельца DOM, polling и dispatch; одновременно два
  клиента на одном корне запускать нельзя
- Live identity resolution/login, баланс, герой/его доступность, награды турнира,
  realtime PubSub, остальные игровые модули и полноэкранная навигация
- GET не содержит свежесть game session/sequence/heartbeat: успешный HTTP
  доказывает только полученный снимок EBS, не свежесть игрового состояния
- Контракт не содержит общего числа раундов, лимита очереди и наград; эти
  числа намеренно не изобретены в новом UI
- Полная доступность/клавиатурный аудит и реальные мобильные устройства
- Производительность относительно legacy: размеры этой сборки измерены,
  ускорение живой панели не заявляется

HTTP-адаптер протестирован на поддельном fetch, а fixture preview на локальных
DTO. До live включения отдельно проверить общую политику длительных/неизвестных
заявок, время жизни dispatcher, auth-resolve, все доступности и release gates.
