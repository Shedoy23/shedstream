# ShedLink — Post-0.1.0 Hardening Plan

**Ревизия 2026-09-04, проверка и уточнения 2026-09-05.** Исходный текст пришёл извне (Codex) и поставил верный
диагноз: платное действие может отчитаться успехом, ничего не сделав, а система
умеет объяснять себя только владельцу. Ревизия сверила каждый пункт с
репозиторием и оставила **дельту**: что уже построено (с путями), что реально
остаётся, чем это удерживается от отката и до какой вехи `ROADMAP.md` должно быть
закрыто.

Ревизия понадобилась потому, что половина исходных пунктов описывала уже
работающие гейты. Это тот самый класс промаха, ради которого заведено правило
«сначала спроси документацию, потом код» (`CLAUDE.md`, workflow §1): дорого не
ошибиться, дорого построить второй дом рядом с существующим и получить две
правды.

Основной вопрос документа не меняется:

> Работает ли ShedLink не только у владельца и под наблюдением разработчика,
> но и как самостоятельный продукт в неизвестных состояниях?

Границы: не добавлять игровые механики, не переписывать работающую архитектуру
без доказанного дефекта.

## Как читать вместе с `ROADMAP.md`

`ROADMAP.md` отвечает «что строим и для кого»: вехи R0…R9, определения метрик
§5, продуктовый дашборд §6. Этот файл отвечает «чем доказываем, что построенное
не врёт». Своей очереди работ у него нет — у каждого пункта стоит веха, до
которой он обязан быть закрыт.

Три пункта исходного текста оказались чужими домами и здесь не живут:

| Было | Где это на самом деле живёт |
|---|---|
| P9 reference integration | `ROADMAP.md` R9 — «Integration SDK, reference integration, compatibility test kit». Осталась дешёвая часть — см. H9 |
| P10 метрики продукта | `ROADMAP.md` §5 (определения TTTR/TTFVA/Activation/Retention) и §6 (дашборд). Там определения точнее, включая §5.2-бис «что TTTR на самом деле мерит» |
| «диагностическая цепочка» P2 | `ROADMAP.md` §5.1 Technical Ready — цепочка описана дословно. Новое в P2 только **объяснение отказа на каждом шаге** |

## Найдено при ревизии — чинить до всего остального

**В каталоге Manager alpha.13 Bannerlord отказывается ставиться на локально
проверенную версию игры 1.4.8.** Распространённость этой версии среди пользователей
по репозиторию не установлена.

- `manifests/installation/bannerlord-0.1.1.json` объявляет
  `game.supported_versions: ["1.3"]`; файл не менялся с релиза 0.1.1
  (`d0256eb`); на момент исходной ревизии `1.4` в каталоге не было.
- Игра на этой машине — `bin/Win64_Shipping_Client/Version.xml` →
  `Value="v1.4.8"`; `compatibility_pattern` из манифеста вырезает из неё `1.4`.
- `GameVersionDetector.Compatibility()` сравнивает строгим `Contains` →
  `"unsupported"`; `MainWindow.xaml.cs:1112-1117` отказывает установке с текстом
  «Bannerlord v1.4.8 не поддерживается. Поддерживаются: 1.3.».
- Manager alpha.13 везёт ту же копию манифеста
  (`dist/releases/ShedLink.Manager-0.1.0-alpha.13-win-x64/Release/bannerlord-0.1.1.json`).

По записям проекта мод переехал на 1.4.8 02.09 (19 патчей из 19, живые прогоны
03–04.09); эта проверка документов не повторяет игровой прогон. Код новый,
контракт совместимости старый — ровно тот класс,
который исходный план называл теоретически, а он уже наступил.

Почему это первое: R3 — чистая установка на незнакомой Windows, R4 — пять чужих
стримеров. Оба упираются в этот отказ на первом же шаге.

Цена починки — новый артефакт и каталог Manager: в старом ZIP была другая DLL,
поэтому одной правки совместимости недостаточно. Локально подготовлены
`BannerlordLink-0.1.2.zip` и `bannerlord-0.1.2.json`; публикация и доставка
каталога пользователям — отдельный шаг. Старый 0.1.1 сохраняется для 1.3.
Новый манифест объявляет семейство `1.4` по существующей схеме детектора;
наблюдения относятся только к **1.4.8**, остальные patch-версии не проверены.

Подпись защищает **идентичность артефакта**, а не весь манифест:
`ArtifactSignatureVerifier.SigningPayload()` включает `integration_id`,
`release_version`, `artifact.id`, `size_bytes`, `sha256`. Изменение одного
`supported_versions` подпись не ломает; новый release_version/архив требует
новой подписи. Защита инструкций установки и каталога остаётся задачей H7.

Записано в `DEFERRED.md`.

## H1. Terminal Result Contract

**Уже есть.**
Контракт описан: `Расширение/docs/MOD_CONTRACT.md` (23.08) — эталон устройства
исхода выбран (shedcolony: обработчик возвращает исход, отвечает диспетчер),
объяснено, почему в Bannerlord иначе, и назван канал `ActionFeedback.PostFailed`.
Умолчание сделано **видимым**: `BannerlordLink/src/MainThreadDispatcher.cs:118-131`
пишет `[action] БЕЗ ЯВНОГО ИСХОДА action_id=…`, когда успех проставлен
умолчанием, — это рабочий список того, что осталось перевести. Возврат денег и
дедуп покрыты тестами: `test_action_ack_refund_order.py`,
`test_special_action_refund.py`, `test_module_delivery_gaps.py`,
`test_queued_ttl_expiry.py`. 42 файла обработчиков из 47 уже упоминают
`PostApplied`/`PostFailed`.

**Остаётся.**
1. Статическая инвентаризация: таблица «платное действие → где называется исход
   → чем наблюдается эффект». Сегодня список существует только в рантайме, то
   есть виден лишь после того, как зритель заплатил.
2. Умолчание `_handlerSuccess = true` живо. Перевести его в отказ для тех
   обработчиков, у которых исход уже явный, — по группам, не разом.
3. `UNKNOWN` как отдельный наблюдаемый исход: сейчас неопределённость
   схлопывается в успех (в моде) либо в рефанд по TTL (в ядре). Оба варианта
   молчат в телеметрии.
4. Линтер: новое платное действие обязано иметь путь к явному исходу.
5. Сохранить исходные денежные инварианты: после доказанного необратимого
   эффекта автоматический возврат запрещён; потерянный ACK требует сверки
   сохранённого результата по `action_id`, а повторный ACK идемпотентен,
   включая рестарт. `UNKNOWN` сам по себе не доказывает право на возврат.
   Контракт распространяется на все Module API интеграции.

**Готово, когда.** Ни одно платное действие в трёх модах не может завершиться
успехом, которого не подтвердил обработчик; счётчик `UNKNOWN` виден в триаже.

**Гейт.** Линтер в `scripts/lint_consistency.py` (рядом с
`check_sold_actions_have_entry`) + характеризационный тест на `UNKNOWN`.
Показать красным на историческом баге до включения.

**Очередь.** Инвентарь и линтер — до R3. Перевод умолчания — по группам, живой
прогон каждой группы, до R4.

## H2. Диагностика для чужого стримера

**Уже есть — больше, чем предполагал исходный план.**

| Кусок цепочки §5.1 | Чем закрыт |
|---|---|
| backend reachable | `main.py:375` `GET /health` (`SELECT 1`, 200/503); Manager опрашивает каждые 15 с (`MainWindow.xaml.cs:780-837`) |
| game detected / version | `GameDetectionService.IsGameRunning()`, `DetectVersion()` |
| integration installed / version | `InstallationInspection`, `FailedProbeIds`, `InstallationReason` |
| heartbeat fresh | `module_liveness.py` (`module_last_seen`, окно 60 с), `GET /v1/module/{id}/status`, строка «Мод на связи · heartbeat N сек назад» |
| test action → module → result → ACK | `POST /v1/manager/diagnostics/test-action` с режимами `ready / refuse / lost_ack` (`routes/manager.py:225-317`, таблица `manager_diagnostic_actions`) |
| машинно-читаемый снимок | `DiagnosticReportBuilder.Build()` — JSON `schema_version:2` с версиями, установкой, рантаймом, последними сообщениями и редакцией токенов (`Redact()`) |
| чек-лист в кабинете | `GET /api/streamer/setup-status` → карточка `#setupCard` в `templates/streamer_dashboard.html`, с `next_step`/`next_hint` |

**Остаётся — три дыры, а не построение модели с нуля.**
1. **Twitch OAuth стримера Manager не проверяет.** Он проверяет только свою
   сессию pairing. Сервер уже обнаруживает ошибки при обновлении токена
   (`oauth_refresh_loop` в `routes/streamer.py`) и запросах Helix
   (`twitch_subs.py`, `eventsub.py`). Отдельная проверка `/oauth2/validate`
   со scope есть в `scripts/preflight.ps1`. Дыра — в передаче результата
   существующих проверок в устойчивое диагностическое состояние и Manager;
   кабинет показывает приближение по сроку `oauth_expires_at`
   (`routes/streamer.py:625-651`). Для чужого стримера это тот же класс: молчит,
   пока не окажется, что месяц ничего не работало.
2. **Нет истории.** Держится только последнее состояние `_runtimeStatus`;
   «сломалось десять минут назад и починилось» неотличимо от «всё хорошо».
3. **Причина отказа есть не на каждом шаге.** Требование остаётся из исходного
   текста: человеческая причина, техническая причина, что сделать, время,
   версия — на каждом FAILED/WARNING.

**Готово, когда.** Незнакомый стример понимает, на каком слое порвано, без SSH.
Это дословно критерий M1 из `ROADMAP.md` («100% ошибок тестовой матрицы
объясняются понятным сообщением и следующим рекомендуемым действием;
диагностический bundle достаточен для удалённого разбора»).

**Гейт.** `test_manager_diagnostics_multigame.py` + матрица R3
(`docs/R3_MATRIX_RUNBOOK.md`): каждая строка матрицы обязана дать текст причины,
а не пустой отказ.

**Очередь.** До R4. Это не «после стабилизации» — без этого пять чужих стримеров
превращаются в пять личных переписок с владельцем.

## H4. Контракт совместимости версий

**Уже есть.** Контракт формализован: `manifests/installation/v1.schema.json` +
манифесты установки с `game.supported_versions`, `game.version`, `game.detection`,
`artifacts[].sha256` и `signature`, `health[]`, у RimWorld и нового Bannerlord 0.1.2 ещё
`compatibility_messages`. Валидатор — `scripts/validate-installation-manifests.py`
(схема; size/sha256 пересчитываются только для `source.kind=repository`).
Для текущих HTTPS-артефактов Python-валидатор не скачивает и не проверяет байты;
это делает Manager при скачивании (`ArtifactVerifier`, `SecureArtifactDownloader`).
Общий прогон валидатора на 05.09 красный: старые `bannerlord-0.1.1.json`,
`shedcolony-0.1.0.json` и `shedcolony-0.1.1.json` отстали от схемы. Новый
`bannerlord-0.1.2.json` проходит отдельно. Валидатор не включён в CI/pre-commit,
а `test-installation-manifests.py` проверяет только один эталонный манифест.
Тесты — `test-installation-manifests.py`,
`test-installation-transaction.py`. Manager отказывает на несовместимой версии с
текстом. Класс «опубликован не тот бинарник» закрыт для shedcolony:
`scripts/check-shedcolony-jar.py` внутри упаковщика сверяет байты jar со списком
платных действий бэкенда.

**Остаётся.**
1. **Манифест никто не сверяет с реальностью** — см. раздел «Найдено при
   ревизии». Нужна проверка: версия игры, на которой мод собран и прогнан, есть
   в `supported_versions` актуального манифеста.
2. **Для Bannerlord и RimLink нет аналога `check-shedcolony-jar.py`.**
   `pack-bannerlord-release.ps1` и `pack-rimlink-release.ps1` печатают sha256
   того, что упаковали, но не отвечают на вопрос «а этот DLL умеет то, что
   бэкенд продаёт». Это тот самый инцидент 28.08, просто с другой игрой.
3. Обратная совместимость бэкенда со старым фронтом на CDN проверяется одним
   тестом (`test_frontend_001_compat.py`); список того, что нельзя ломать, нигде
   не собран.
4. Сохранить полную матрицу протоколов: extension ↔ backend schema ↔ Manager ↔
   installation manifest ↔ module ↔ game. Наличие полей версии ещё не доказывает
   совместимость комбинации. Для каждого поддержанного релиза нужны связь
   source/build/published bytes и явный отказ на неподдержанной комбинации.
5. Устранить schema drift старых манифестов и включить проверку всего каталога
   в CI; проверку HTTPS bytes проводить отдельным артефактным гейтом.

**Готово, когда.** Упаковщик любого мода валит сборку, если бинарник не умеет
проданного или объявленная версия игры разошлась с проверенной.

**Гейт.** Проверки внутри `pack-*.ps1` (exit ≠ 0 останавливает упаковку) +
строка в `scripts/lint_consistency.py` про манифест ↔ COMPAT_MATRIX.

**Очередь.** Пункт 1 — немедленно (блокирует R3). Пункт 2 — до R4. Пункт 3 —
после R4.

## H5. Наблюдаемость и безопасная деградация

**Уже есть.** Частичные отказы частично закрыты: авто-рефанд зависших команд по
TTL (`rimworld.py:314-330`), общий путь возврата в `module_ack`
(`routes/module_api.py:538+`), гейт «мод офлайн» (`test_mod_offline_gate.py`),
устойчивость фоновых циклов и пула БД (`test_background_loops_survive.py`,
`test_db_pool_resilience.py`), аварийная остановка действий в кабинете (на проде
с 01.09), журнал движения крустиков (`test_points_ledger.py`, миграция m118),
разовый пост-деплойный аудит `ops/production/postdeploy_db_audit.py` со счётчиком
`module_action_statuses`.

**Остаётся.** Ни одна из перечисленных величин не измеряется постоянно: нет
возраста очереди, нет самого старого неподтверждённого платного действия, нет
latency ACK и рефанда, нет счётчика ошибок по модулю. Есть данные (таблицы
`module_actions`, `manager_diagnostic_actions`, `module_last_seen`), нет ни
агрегата, ни эндпоинта, ни порога.

Сохранить и остальные сигналы исходного плана: ошибки по каналу, задержка БД,
рост backlog, возраст бэкапа и состояние диска. Матрица деградации включает
slow DB, stale heartbeat, dead worker, растущую очередь, частичный отказ backend,
один проблемный tenant и давление логов/диска. Перед реализацией каждого сигнала
сверить существующие проверки; этот список не утверждает их полного отсутствия.

Главный инвариант оставить как в исходном тексте:

> Если ShedLink не способен доказать безопасное исполнение платного действия,
> новое платное действие должно fail closed.

**Готово, когда.** Один эндпоинт отдаёт эти величины, и превышение порога само
закрывает продажу действий, а не ждёт, что кто-то посмотрит.

**Гейт.** Тест: при искусственно состаренной очереди покупка отклоняется с
внятной причиной (`fake-mod.py` умеет исчезнуть посреди команды — этого хватает,
чтобы показать тест красным).

**Очередь.** После R4, вместе с H3.

## H8. Инварианты, проверяемые машиной

**Уже есть — частичное покрытие инвариантов.** В
`scripts/lint_consistency.py` 25 проверок, среди них:
`check_tenant_scoping` (арендатор), `check_refusal_codes_have_text` (у отказа
есть текст для зрителя), `check_currency_boundary` и
`check_declared_gold_is_charged` (валюты), `check_migrations_wired` и
`check_migrations_self_register` (миграции), `check_manifest_events` и
`check_manifest_actions` (манифест), `check_status_is_a_window`,
`check_runbook_health`, `check_rule_links` (документы). Артефакт против
исходника — `check-shedcolony-jar.py`. Заморозка фронта на время ревью —
исполняемый гейт `$FrontendReviewOpen` в `scripts/deploy.ps1`: prod frontend
deploy прекращается до упаковки/отправки; исключение через `-CriticalReason`
записывается в журнал. `RELEASE_RECORD.md` описывает процесс.
Размер/hash и подпись скачанного артефакта проверяет Manager, с тестами в CI.
Маркер отсутствующего исхода Bannerlord уже входит в `FATAL_ALARMS`
`scripts/triage-mod-log.py`; статической проверки это не заменяет.

**Остаётся — закрыть разницу между частичным гейтом и полным инвариантом.**
1. Статический гейт явного исхода платного действия (см. H1).
2. Связь проверенной версии игры, сборки и опубликованного релиза (см. H4),
   плюс включение валидатора всего каталога в CI.
3. Проверка свежести состояния freeze: ручной `$FrontendReviewOpen` и версия
   в сообщении должны соответствовать открытому ревью в release record.
4. Не потерять требование **не менять применённые миграции**:
   `check_migrations_wired` проверяет подключение, а
   `check_migrations_self_register` — запись в `migrations_applied` и commit;
   это не проверка неизменности уже применённого файла. Нужен отдельный гейт
   относительно принятого baseline либо явно описанный эквивалент.
5. Для движения валюты требовать ledger evidence (m118 и
   `test_points_ledger.py`); валютные линтеры сами по себе этого не доказывают.
   Составить покрытие путей изменения баланса и установки интеграций, прежде
   чем утверждать, что все восемь исходных инвариантов закрыты.

**Готово, когда.** Для каждого исходного инварианта названы исполняемый гейт,
область покрытия и отрицательная проверка; недостающие гейты подключены к CI.
Для исторических дефектов проверка показана красной до исправления.

**Гейт.** Сам линтер, он же в pre-commit и CI.

**Очередь.** Следует за H1 и H4 — отдельной работы почти нет.

## Ограничения для агента

### След проверки 05.09

Локальный кэш workflow `wf_2f7229d2-fbc` содержит 62 проверенных утверждения,
9 подтверждённых проблем и завершённые check/refute; повторять их не пришлось.
Повтор после лимита сохранил результаты: незавершённым остался только
`critic:completeness`. Его часть завершена сверкой документа с сохранённым
конспектом `ORIGINAL` в скрипте workflow. Восстановлены требования об эффекте
до возврата, идемпотентности через рестарт, полной матрице версий, дополнительных
сигналах/сценариях деградации, Manager keys, неизменности миграций и ledger evidence.
Исходник до ревизии не сохранился в этом workflow: полнота установлена относительно
его конспекта, а не неизвестного оригинала. Нового игрового, production или DR
прогона эта документальная проверка не утверждает.

Сохранено из исходного текста, потому что совпадает с правилами проекта.

Агент может автономно: исследовать код, строить инвентари и матрицы, писать
тесты, линтеры и harness, реализовывать диагностику, делать fake/reference
модули, проверять совместимость, готовить процедуры восстановления и аудиты
безопасности, предлагать патчи, прогонять доступные CI/E2E.

Агент **не** считает доказанным: удобство для чужого стримера; retention и
продуктовую ценность; игровой эффект, который не наблюдается через доступный
harness; исход ревью Twitch; disaster recovery без контролируемого прогона;
опасные изменения на проде. Для них он готовит процедуру и доказательства, а
подтверждение оставляет человеку.

Добавлено ревизией:

- **Перед пунктом — `python scripts/docs-search.py <тема>`.** Половина исходного
  плана описывала существующие гейты; это дешевле проверить, чем построить.
- **Фикс без названного механизма — гипотеза, а не решение**, и помечается так
  же и в сводке, и в файле.

Основной принцип оставлен без изменений:

> Не спрашивать «есть ли тест?»
> Спрашивать «какое утверждение о системе этот тест действительно доказывает?»
