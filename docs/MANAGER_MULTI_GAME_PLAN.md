# Manager для остальных игр — что реально мешает

Дата: 2026-08-16. Повод: решение владельца выложить Manager на сайт, когда
через него будут ставиться моды всех игр.

## Принцип (решение владельца, 2026-08-16)

> Manager не привязан ни к какому конкретному моду. Это платформа, которую
> будем расширять.

## Итоговый пользовательский контракт (решение владельца, 2026-08-16)

Новый стример скачивает один ShedLink Manager. Дальше Manager сам:

1. находит установленные поддерживаемые игры;
2. показывает доступные для них интеграции понятными названиями;
3. подключает Twitch без ручной передачи токенов;
4. выбирает совместимый подписанный релиз мода;
5. скачивает, проверяет и устанавливает все необходимые файлы;
6. создаёт и обновляет конфигурацию, включая channel id и защищённый ключ;
7. не затирает чужие настройки и безопасно откатывается после сбоя;
8. запускает проверку связи с настоящим модом и показывает готовность;
9. позже сам предлагает безопасные обновления Manager и интеграций.

Допустимые действия стримера: скачать/запустить Manager, войти через Twitch,
выбрать интеграцию и при необходимости указать папку игры. Ручные JSON, XML,
API URL, module token, копирование DLL и инструкции «положите файл туда» —
дефект продукта, а не нормальный сценарий.

Технические решения, миграции состояния, безопасность ключей, совместимость,
откаты и доказательство тестами находятся на исполнителе. Владелец принимает
продукт по пользовательскому пути и результату, а не по устройству кода.

Практический критерий, по которому проверяется любая правка Manager: если для
поддержки новой игры пришлось тронуть код Manager, а не положить манифест —
правка сделана не там. Единственные допустимые исключения — новый *вид*
описания (например, невиданный ранее формат конфига), и тогда расширяется
контракт, а не добавляется ветка про конкретную игру.

Вторая интеграция выбрана: **Bannerlord** (решение владельца 2026-08-16).

## Короткий вывод

Архитектура уже почти позволяет это: манифест установки описывает игру, поиск
папки, поддерживаемые версии, артефакт, подпись и проверки здоровья. Мешает не
архитектура, а шесть мест, где код игнорирует манифест и знает про RimWorld
напрямую. Пока они существуют, «добавить игру» означает править код Manager, а
не положить файл.

## Где именно прибито к RimWorld

| Файл | Что знает про RimWorld |
|---|---|
| `Core/Detection/RimWorldDetectionService.cs` | ищет в Steam папку по имени `RimWorld`, проверяет `RimWorldWin64.exe` и `Mods` |
| `Core/Detection/GameVersionDetector.cs` | версия читается из `Version.txt` — способ, специфичный для RimWorld |
| `Core/ManagerCoordinator.cs` | module id `rimworld` |
| `Core/State/ManagerState.cs` | тот же id по умолчанию |
| `App/ReleaseConfiguration.cs` | константа игры `rimworld` |
| `App/MainWindow.xaml(.cs)` | тексты и весь сценарий написаны под одну игру |

Манифест при этом уже содержит `detection` (Steam app id `294100`, ручная
проверка по списку файлов) и `supported_versions` — то есть нужные данные есть,
их просто не читают.

## Что придётся расширить в контракте

1. **Способ определения версии игры** — сейчас жёстко `Version.txt`. Нужен
   описанный в манифесте вариант: файл + шаблон, или чтение из другого места.
2. **Хранилище настроек мода** — загрузчик манифестов сегодня принимает только
   `xml` в `windows_local_low`. У Bannerlord и MineColonies настройки лежат
   иначе, поэтому понадобятся другие `kind` и базовые папки. Это правка схемы
   и валидатора, а не всего установщика.
3. **Выбор игры в интерфейсе** — сейчас Manager ведёт одну игру от начала до
   конца. Нужен список установленных игр и переключение между ними.

## Чего НЕ придётся трогать

Транзакция установки, откат, восстановление после обрыва, проверка подписи,
безопасная распаковка, работа с ключами и диагностика от игры не зависят —
они уже написаны обобщённо. Это и есть проверка гипотезы «80% платформа».

## Внешняя зависимость, которую нельзя обойти кодом

Для каждой новой игры нужен **подписанный опубликованный архив мода** по
неизменяемой HTTPS-ссылке — как `RimLink-0.1.1.zip`. Это ручная операция с
production и приватным ключом, она требует отдельного подтверждения владельца.

Проверено 2026-08-16: сами моды формат ключа не знают — они отправляют строку
из своего конфига, а разбирается бэкенд. Значит переписывать моды под новый
ключ не нужно; нужно лишь, чтобы приём событий этой игры на бэкенде принимал
`slmod_v1`, как уже сделано для RimWorld.

   знает; возврат к жёсткой папке `RimWorld` тест роняет. Поведение RimWorld
   не изменилось, факты переехали из кода в `rimworld-0.1.1.json` и схему.

   значения `channel_id`. Транзакция записи (журнал, резервная копия, права

   чтение XML, зелёный подтверждает Bannerlord `v1.3.15 → 1.3` и прежнее

   перезаписывает RimWorld. `RimWorldDetectionService` удалён, имён конкретных
   игр в коде приложения больше нет. Осталось подписать/опубликовать

5. **Выпуск сделан 2026-08-16.** BannerlordLink `0.1.0` подписан, опубликован

   `0.1.0-alpha.4` с обоими подписанными манифестами. Остался живой запуск

6. **Живая установка сделана 2026-08-19.** Первый прогон показал красный отказ

   административной привилегии обычный пользователь успешно установил мод;

## Что конкретно нужно для шага 2 (проверено по коду мода)

`BannerlordLink/src/Net/BackendConfig.cs` хранит настройки в **плоском
`config.json`** собственного разбора (без вложенности, чтобы не тащить лишнюю
библиотеку) с ключами `backend_url`, `module_token`, `channel_id`,
`poll_interval_ms`. RimWorld же настраивается XML в `windows_local_low`.

Отсюда три расширения контракта, все — новые *виды*, не ветки про игру:

- `configuration.store.kind`: добавить `json` к существующему `xml`;
- базовая папка конфига: сегодня разрешён только `windows_local_low`;
- источник значения: сегодня есть `backend_url` и `channel_module_token`,
  Bannerlord дополнительно требует `channel_id`.

Записать отдельно: заглушка `RimWorldDetectionService` — единственное место в
Core, называющее игру. Пока она жива, принцип соблюдён не полностью.

## Найдено 2026-08-16: контракт не умеет читать версию Bannerlord

Попытка написать манифест Bannerlord упёрлась в чтение версии игры.
`GameDetectionService` берёт **первую непустую строку файла** и прикладывает к
ней регулярное выражение, возвращая совпадение целиком. Для RimWorld это
работает: `Version.txt` из одной строки. У Bannerlord версии нет ни в одном
файле, где она стояла бы первой строкой:

| Файл | Первая непустая строка | Что получится |
|---|---|---|
| `bin/Win64_Shipping_Client/Version.xml` | `<Version>` | цифр нет → версия не определяется, установка закрывается |
| `Modules/Native/SubModule.xml` | `<?xml version='1.0' encoding='utf-8'?>` | шаблон вида `\d+\.\d+` поймает **1.0** — версию XML, а не игры |

Второй случай хуже первого: он не ломается, а тихо врёт. Настоящая версия
установленной игры — `v1.3.15`, лежит второй строкой в обоих файлах.

**Значит манифест Bannerlord писать пока не на чем**, и публиковать архив
раньше манифеста бессмысленно: подписывается именно манифест.

**Починка (небольшая, но в работающем пути RimWorld):** искать по всему файлу,
а не по первой строке, и разрешить шаблону группу захвата — тогда
`Value="v(\d+\.\d+)"` пришпилит версию однозначно, вместо того чтобы ловить
первое похожее число. Делать это надо с доказательством, что поведение
RimWorld не изменилось.

**Решение владельца 2026-08-16:** ожидание тестировщика отменено; Manager
готовим как платформу для всех модов. Исправление выполнено с обязательным
красно-зелёным тестом. Уже собранный `alpha.3` остаётся неизменным артефактом;
multi-game изменения войдут в следующую сборку.
