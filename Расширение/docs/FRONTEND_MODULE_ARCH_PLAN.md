# План: ядро + игровые модули во фронте

Создан: 2026-08-19. Автор анализа — рабочая сессия по запросу владельца
«как сделать так, чтобы сложность добавления игры росла медленнее
количества игр».

**Статус: шаги 1–3 сделаны (1–2 — 2026-08-19, 3 — 2026-08-20), шаги 4–5 впереди. Правки фронта живут в
репозитории, но НЕ выезжают на прод до вердикта Twitch по `0.0.2`: поданный
архив пришпилен тегом `submit/0.0.2` и правками в рабочем дереве не меняется,
на ревью влияет только деплой.** Механизм, а не обещание: `scripts/deploy.ps1` теперь
блокирует `-Frontend` флагом `$FrontendReviewOpen` (см. §7).

---

## 1. Что оказалось правдой, а что нет

Исходная гипотеза владельца: «фронт плохо масштабируется, добавление игры
дорожает, нужны универсальные компоненты и адаптеры».

Проверка по коду её **не подтвердила в той части, что про стоимость
добавления игры**, и подтвердила в другой, более дорогой.

### Сколько стоила третья игра

Коммит `a7c7b20` (25.06.2026), фронт ShedColony целиком:

| Файл | Строк |
|---|---|
| `viewer-shedcolony.js` (новый) | +249 |
| `viewer.js` (ветка в switcher) | +14 |
| `extension.html` | +7 |
| `mobile.html` | +7 |

То есть **проводка новой игры в оболочку — около 28 строк в трёх файлах**.
Это уже дёшево. Универсальные компоненты этот счёт почти не уменьшат.

### Что дорого на самом деле

| Проблема | Замер | Чем платим |
|---|---|---|
| Ядро протекает Bannerlord'ом | 262 строки из 2595 в `viewer.js` упоминают bannerlord/`_bnr` (строки 1123–2444), ~40 функций `_bnr*` | правка одной игры трогает общий файл всех игр |
| Платный путь копируется на каждую игру | 3 несовместимые реализации | **деньги зрителя** |
| Разметка Bannerlord и RimWorld дублируется | статичный HTML в `extension.html` **и** `mobile.html` | забыл один — половина аудитории видит старое |
| Плоское глобальное пространство имён | `viewer.js` 74 глобальных имени, `viewer-bannerlord.js` 72, `viewer-rimworld.js` 17, `viewer-shedcolony.js` **0** | коллизия `_buyItem` 22.07 сломала покупки в магазине на час |

### Три копии платного пути и что каждая потеряла

| | Bannerlord (`_bannerlordBuyAction`, viewer.js:1954) | ShedColony (`_buy`, viewer-shedcolony.js:316) | RimWorld (свой эндпоинт на действие) |
|---|---|---|---|
| `client_action_id` (защита от двойного списания) | да | да, свой формат | **нет** |
| кулдаун, присланный сервером | да | нет | свой, клиентский |
| отказ по роли (мод/стример) | да | нет | нет |
| обновление баланса после покупки | да | **нет** | да |
| защита от дабл-клика | да | да | да |

Механизм расхождения простой и повторяемый: новая игра копирует ближайшую
реализацию и берёт не всё. Универсальный `HealthBar` этот механизм не
трогает вообще.

### Дефекты, найденные по дороге

1. **Панель Колонии показывает устаревший баланс.** `_buy` на успехе не зовёт
   `loadUserData()`. Баланс рисуется из `_cachedUserPoints`, который
   обновляется общим тиком раз в 60 с; вдобавок `_renderIfChanged`
   перерисовывает панель только при изменении состояния колониста, так что
   врать может и дольше. Зритель видит непотраченные крустики и жмёт второй
   раз. Записано в `DEFERRED.md`, чинится шагом 1.
2. **`test_frontend_module_lifecycle.py` не покрывал ShedColony** — регулярка
   cache-bust перечисляла только `viewer.js`/`-bannerlord`/`-rimworld`.
   Исправлено 19.08 (§7).
3. **Заморозка деплоя истекла сама по себе.** `$FreezeUntil` в `deploy.ps1`
   стоял на 2026-07-28 и был неактивен ровно тогда, когда идёт новое ревью.
   Исправлено 19.08 (§7).

## 2. Целевая архитектура

Меньше, чем предлагалось в исходной идее.

```
core (viewer.js)
  |- auth / баланс / вкладки / тосты          <- уже есть
  |- ShedLink.games.register(id, {start, stop})  <- шаг 2
  |- ShedLink.buyAction(game, type, data)        <- шаг 1
  |     кулдаун . идемпотентность . role-gate . тост . обновление баланса
  \- мелкие общие рисовалки (бар, цена, аккордеон)  <- шаг 4

games/<игра>.js — IIFE, ноль глобальных имён, сам рисует свой корневой div
```

Инвариант, к которому идём: **добавление игры = один новый файл-IIFE + одна
строка `register(...)` + один пустой `<div>` в двух оболочках.**

## 3. Что сознательно НЕ делаем

Записано, чтобы через месяц не обсуждать заново.

| Отвергнуто | Почему |
|---|---|
| `capabilities: {skills: true, health: true}` во фронте | ни один общий экран не спрашивает «умеет ли игра скиллы» — каждая игра рисует свою панель целиком. Абстракция без потребителя. **Что вернёт вопрос:** появление экрана, который ядро рисует по данным нескольких игр сразу. |
| Адаптеры `GameAPI -> Common UI Model` | адаптер окупается, когда общая модель кормит общие компоненты. Общий компонент здесь пока один — полоска. |
| Второй manifest во фронте | manifest уже есть на бэкенде (`backend/modules/<игра>/manifest.yaml`). Вторая копия = вторая правда. |
| Общий `SkillList` | скиллы есть у RimWorld и ShedColony, у Bannerlord вместо них фокусы/атрибуты/перки. Двух похожих мало. |
| Vite / бандлер | отдельная сборка = новый артефакт на ревью Twitch. Не смешивать с рефакторингом. Вернуться, когда число файлов начнёт мешать, а не «на будущее». |
| Большой rewrite фронта | `DEFERRED.md`: масштабный frontend redesign не подтверждён данными. |

## 4. Порядок работ

Каждый шаг обязан заканчиваться доказательством, а не выводом.

### Шаг 1 — один платный путь — СДЕЛАНО 2026-08-19

Перенести `_bannerlordBuyAction` в ядро как `ShedLink.buyAction(game, type, data)`,
тело не менять — эндпоинт становится параметром. Bannerlord зовёт его,
ShedColony переключается на него (попутно чинится дефект №1). RimWorld в этом
шаге не трогаем: у него другой протокол.

**Как сделано.** Новый файл `frontend/viewer-actions.js` — IIFE, ноль
глобальных функций, namespace `window.ShedLink`. При загрузке не трогает
`document`, зависимости берёт из global в момент вызова, поэтому тестируется
в node без браузера. `_bannerlordBuyAction` и ShedColony `_buy` стали
обёртками на 5–10 строк; отличия игр вынесены в параметры (`successMessage`
для отложенных действий, `onCooldown`/`cooldownAttr`, `onSuccess`,
длительности тостов). Убраны две локальные копии single-flight
(`_bnrInflight`, `_inflight`) — теперь один на пару «игра+действие».

**Доказательства (2026-08-19):**

| Проверка | Результат |
|---|---|
| `node tests/test_buy_action.js` — 22 утверждения | exit 0 |
| тот же тест с ВЫРЕЗАННЫМ `loadUserData()` (дефект ShedColony) | exit 1, назвал: «после успешной покупки баланс крустиков перечитывается» |
| `node --check` пяти viewer-модулей | exit 0 |
| `python scripts/lint_consistency.py` | exit 0 (5 warning — известный долг цен, не мой) |
| `python scripts/run-backend-tests.py` | ВСЕ ЗЕЛЁНЫЕ: 50, exit 0 |
| настоящий браузер, локальная копия, клик по кнопке Bannerlord | POST `/api/bannerlord/action` 200, действие в очереди с UUID `81e0749f-…` |
| настоящий браузер, клик в панели Колонии | POST `/api/shedcolony/action` 200, отказ бэкенда показан («заявка уже в очереди») |

**Что поймал ТОЛЬКО браузер — и это важнее всех зелёных тестов.** Первая
версия общего пути брала зависимости через `window.API_URL` / `window.authToken`.
Node-тест был зелёный, а в браузере покупка уходила на
`undefined/api/shedcolony/action` → 405. Причина: `const API_URL` и
`let authToken` объявлены на верхнем уровне классического `<script>` и **не
становятся свойствами `window`** — они живут в общей лексической области
скриптов. То есть в проде это сломало бы КАЖДУЮ покупку в обеих играх.
Исправлено: зависимости берутся по имени. Тест переписан на `vm`-контекст,
который воспроизводит эту разницу, и теперь падает ровно так же
(`получено: undefined/api/bannerlord/action`).

**Урок в копилку:** «зелёный юнит-тест» и «работает у зрителя» — разные
утверждения, когда тест не воспроизводит среду. Node-`require` не
воспроизводит плоские `<script>`; `vm` — воспроизводит. Две ловушки самой
локальной проверки (worktree в `FRONTEND_PATH`, кэш браузера по `?v=`)
записаны в `RUNBOOK.md` §10.

**Побочно исправлено:**
- дефект ShedColony «устаревший баланс после покупки» — общий путь всегда
  перечитывает баланс;
- `scripts/run-backend-tests.py` не видел `.js`-тесты — тест существовал бы, но
  никто бы его не запускал. Теперь ранер берёт `test_*.py` и `test_*.js`.

**Что при переезде изменилось намеренно** (не регрессии, но знать надо):
- у ShedColony появилась проверка авторизации перед платным запросом и приход
  role-gate/кулдауна, если бэк начнёт их присылать;
- сетевая ошибка теперь возвращает `null` вместо `undefined` — все вызывающие
  проверяют `if (res && res.success)`, проверено по всем 40 местам;
- в перенесённом коде удалена мёртвая переменная `roleLabel` (вычислялась и
  никогда не читалась).

### Шаг 2 — реестр вместо `if/else` — СДЕЛАНО 2026-08-19

`switchIntegrationModule` перестаёт знать имена игр: игры регистрируются
сами (`register('bannerlord', {root, start, stop})`), ядро гасит все,
кроме активной. Это же убирает класс инцидента 03.08 (панель Bannerlord
опрашивала RimWorld тысячами запросов, потому что у RimWorld опрос
стартовал при парсе файла).

**Как сделано.** `frontend/viewer-registry.js` — IIFE, ноль глобальных имён.
Игра объявляет себя сама: `ShedLink.registerGame(id, {rootId, title, start,
stop})` из своего файла. `switchIntegrationModule` в ядре стал одной строкой и
больше **не содержит ни одного имени игры**. Инвариант «активна не более одной,
все остальные остановлены» записан один раз в реестре.

Заодно ушли два прежних недостатка: раньше отсутствие ОДНОГО элемента в
оболочке прерывало переключение целиком (`if (!empty || !rim || !bnr) return;`)
— теперь отсутствующие блоки просто пропускаются, а игра всё равно гасится;
и падение внутри одной игры больше не оставляет панель в состоянии «старая
остановлена, новая не запущена».

**Доказательства (2026-08-19):**

| Проверка | Результат |
|---|---|
| `node tests/test_game_registry.js` — 22 утверждения поведения | exit 0 |
| тот же тест с возвращённым классом бага 03.08 (гасим только «соседа») | exit 1: «остановлены ВСЕ игры (получено: ["stop:beta"])» |
| `python scripts/run-backend-tests.py` | ВСЕ ЗЕЛЁНЫЕ: 52, exit 0 |
| `node --check` шести viewer-модулей · линтер | exit 0 |
| настоящий браузер: `ShedLink.registeredGames()` | `["bannerlord","rimworld","shedcolony"]` |
| настоящий браузер: смена игры на бэке → перезагрузка профиля | панель переключилась, подпись сменилась, `_bannerlordPollId === null` — опрос Bannerlord реально остановлен |
| обратное переключение | панель и опрос вернулись, `_activeIntegrationModule === 'bannerlord'` |

**Проверка «неактивная игра не опрашивается» переехала из строк в поведение.**
Прежний тест искал в исходнике `switchIntegrationModule` строки вида
`window._stopRimworldPolling` и считал их количество — такая проверка зеленеет
и тогда, когда до этих строк не доходит управление. Теперь инвариант проверяет
`test_game_registry.js` вызовами, а в `test_frontend_module_lifecycle.py`
осталась только проводка: ядро делегирует в реестр, каждая игра объявляет себя.

**Что теперь стоит добавление игры во фронт:** файл-IIFE + одна строка
`registerGame` + пустой `<div>` и один `<script>` в двух оболочках. Ядро не
правится вообще.

### Шаг 3 — вынести Bannerlord из ядра — СДЕЛАНО 2026-08-20

262 строки `_bnr*` из `viewer.js` переезжают в `viewer-bannerlord.js`,
файл оборачивается в IIFE (как ShedColony), наружу торчит только то, что
зовёт ядро.

**Как сделано.** 805 строк Bannerlord (стейт, кулдауны, аффорданс, модалки,
поллинг, диспетчер покупок) переехали в `viewer-bannerlord.js`. Ядро с 2444
строк ужалось до 1645, упоминаний Bannerlord в нём было 243, осталось 5 — и все
пять это комментарии.

Перед переносом посчитал, что из 54 объявленных в блоке имён используется
кем-то, кроме `viewer-bannerlord.js`: ровно ОДНО — `switchIntegrationModule`,
и оно осталось в ядре. Остальное было Bannerlord-приватным и просто лежало в
общем файле.

**Доказательства (2026-08-20):**

| Проверка | Результат |
|---|---|
| `node --check` viewer.js и viewer-bannerlord.js | exit 0 |
| линтер коллизий глобальных имён | exit 0 |
| `python scripts/run-backend-tests.py` | 52/52, exit 0 |
| настоящий браузер: панель Bannerlord | 71 кнопка — столько же, сколько до переноса; герой отрисован; поллинг идёт; диспетчер и кулдаун живы |
| новых ошибок в консоли на текущей сборке | ноль |
| клик по платному действию | ушёл на бэкенд, действие в очереди с новым UUID |

**Что поймал `test_frontend_module_lifecycle.py` по дороге:** он вырезал тело
`switchIntegrationModule` до соседнего заголовка `// ===== Daily rewards…`,
а этот заголовок уехал вместе с Bannerlord-кодом. Проверка молча начала читать
ВЕСЬ остаток ядра и упала на комментарии. Конец функции теперь ищется по её
закрывающей скобке. Класс: **маркер, привязанный к соседу, а не к самому
объекту** — переживает ровно до первого переезда соседа.

**Чего НЕ сделал и почему.** Обёртка `viewer-bannerlord.js` в IIFE (как у
ShedColony) в этот шаг не вошла. Файл объявляет 72 глобальных имени, часть из
них зовётся из ядра и из inline-обработчиков в оболочках; заворачивать это
одним движением — риск, несоразмерный выгоде на сегодня. Отдельным шагом, когда
будет чем проверить каждый вызов.

### Шаг 4 — общие мелочи

Аккордеон с запоминанием (`_bnrCard`/`_grp`), внутренние вкладки

### Шаг 5 — RimWorld на общий протокол

Перевести на `POST /api/rimworld/action` с `{action_type, data}`, как у
двух других игр. Тогда `client_action_id` появляется у него бесплатно.
Низкий приоритет: RimWorld сейчас фактически выключен.

## 6. Ограничения, которые действуют прямо сейчас

- Фронт Extension `0.0.2` на ревью Twitch с 16.08, архив зафиксирован тегом
  `submit/0.0.2`. Правки в репозитории поданный архив не меняют, **деплой
  фронта на прод — меняет** (и попутно перебивает cache-bust). Поэтому
  деплой фронта заблокирован механически, см. §7.
- Бэкенд-деплой во время ревью разрешён и обязан обслуживать одновременно
  публичную `0.0.1` и поданную `0.0.2`.

## 7. Что уже сделано 2026-08-19

- **Заморозка деплоя перевыпущена и сужена до фронта.** Был
  `$FreezeUntil = 2026-07-28` — дата протухла сама и оставила прод открытым
  во время нового ревью. Стало: флаг `$FrontendReviewOpen` в
  `scripts/deploy.ps1`, снимается руками в день вердикта. Блокируется только
  `-Frontend`; `-Backend` во время ревью разрешён.
  Проверено в двух состояниях: `deploy.ps1 -Frontend` -> exit 1 с
  объяснением; `deploy.ps1 -Frontend -DryRun` -> проходит, файлы оболочек
  не изменены (md5 совпал).
  **Класс ошибки: срок годности у защиты.** Дата-предохранитель протухает в
  опасную сторону (молча перестаёт защищать), флаг — в безопасную (продолжает
  блокировать, пока человек не снимет). Где выбор есть — брать флаг.
- Найденные дефекты и решения записаны в `DEFERRED.md`.
